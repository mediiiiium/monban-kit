# monban-kit

> **注意：v1 は高リスクの秘密を預けるためのものではありません。** root からは守れず、ターミナルの承認は同じユーザーのエージェントにも真似できます（事故防止で、強い承認ではない）。詳しくは [docs/v1-plan.md](docs/v1-plan.md) の「これで防げないこと」。

monban（門番）= gatekeeper。自分用のパスワード管理の構成。人は Bitwarden の個人金庫と自動入力で、スクリプトや AI エージェントは門番（許可リスト・承認・キルスイッチ）を通して Secrets Manager から鍵を使う。人の複数デバイス（Mac・スマホなど）は、個人金庫の同期で賄う。

- 人：Bitwarden の個人金庫。アプリと自動入力で、人がログインする。門番は通さない
- 手元のエージェント・スクリプト・CI：Secrets Manager から、門番経由
- 離れた場所のエージェント：Bitwarden Agent Access

## 2つの置き場と振り分け

| | 個人金庫（パスワードマネージャー） | Secrets Manager |
|---|---|---|
| 入れるもの | サイトのログイン情報（URL・ユーザー名・パスワード・ワンタイムコード） | 名前と値だけの秘密（API キー・トークンなど） |
| 使うのは | 人（アプリ・拡張機能の自動入力） | 機械（マシンアカウント＋合言葉） |
| 出し分け | できない。マスターパスワードで開ければ全部見える | できる。プロジェクト単位・読むだけ、合言葉ごとに絞れる |
| 置くものの目安 | 自分がログインするもの | プログラム・エージェント・スクリプト・CI が使うもの |

- 人の側は Bitwarden を普通に使うだけ。足す決まりは1つ：エージェントに渡すかもしれない秘密は、個人金庫に入れず Secrets Manager（組織 `monban`）に置く
- 分ける理由：エージェント用の秘密を個人金庫に入れると、渡すときに金庫ごと開ける形になる。Secrets Manager なら、漏れても被害はそのプロジェクトの中だけで、合言葉を止めれば締め出せる
- 同じサービスに人もエージェントもログインするとき（上ほど勧める）：
  1. エージェント用に別の資格情報（API キーなど）を発行し、Secrets Manager に置く。人のパスワードは個人金庫だけ。止めるときはエージェント用だけ失効できる
  2. 個人金庫のログインを Agent Access 経由で使わせる（ログインごとに人が承認。複製を作らない）
  3. 同じパスワードを両方に入れるのは最後の手段（漏れたときの被害が人のログインに直結し、変えるときは2か所直すことになる）

やり取りの記録：[docs/muse-note-two-vaults.md](docs/muse-note-two-vaults.md)

設計と経緯は [docs/design.md](docs/design.md)。

## いまの段階（2026-11-12）

**門番 v1 の10段を作り終えた。まだ高リスクの秘密は扱わない。** 本番の形（別ユーザー `_monban` の launchd のデーモン。`scripts/install.sh` で入れる）で、本物の合言葉とダミーの秘密 `MONBAN_TEST` で動かしている。

- `bws` だけで足りるかを試した：足りない。同じユーザーで動く限り、合言葉はどの置き方でもエージェントから取れた（[docs/first-secret-trial.md](docs/first-secret-trial.md)）。だから門番を書くことにした
- 門番 v1 は10段すべて作った（[docs/v1-plan.md](docs/v1-plan.md)）。どの段も、人のターミナルで確かめてから次へ進んでいる
  - 済み：ソケット（相手の uid の照合）・`bws` で取り出す・許可リスト・コマンドへの注入（`monban run`）・承認（Pushover で知らせ、`monban approve`）・ログのハッシュ連鎖（`monban verify-log`）・キルスイッチ（`monban stop`）・常駐化（`_monban` と launchd）
  - 10段目：2026-11-11 に、本番の形（launchd のデーモン・`_monban`・`bws` の子）で、root の対照つきで確かめた。root でない本人の uid からは、合言葉は `ps eww` で見えず（取り出しの最中の `bws` の子を3回捕まえて3回とも）、合言葉のファイルも読めなかった。同じ瞬間に root からは見えた。見たのは `ps` の道とファイルの権限だけで、root には守れない（[docs/production-check.md](docs/production-check.md)）
- 2026-11-12 に、最初の本物の秘密を入れた（[docs/first-real-secret.md](docs/first-real-secret.md)）。手元用に新しく作った Pushover のアプリのトークン（`PUSHOVER_TOKEN`）で、漏れても通知を送られるだけのもの。注入先は root の持ち物の場所に置いた専用のコマンド（[tools/pushover-notify](tools/pushover-notify)。トークンを出さない）。人のターミナルから承認つきで通り、トークンは画面に出なかった
  - 同時に合言葉を替えた：マシンアカウントを新しく作り（`local-notify` と `MONBAN_TEST` のプロジェクトを読むだけ）、古いマシンアカウントは合言葉を取り消した後に消した
  - 同じ日に Claude Code からも使った：名札 `claude` が承認の画面とログに出て、承認つきで通った。スマホに届いた
- v1 は高リスクの秘密を扱わない。ターミナルの承認は事故防止で、強い承認ではない（[docs/v1-plan.md](docs/v1-plan.md) の「これで防げないこと」）
- 人の側（Bitwarden の個人金庫を普段使いにする）の手順を書いた（[docs/human-side.md](docs/human-side.md)）。エージェントに渡すものを分けるには手元の秘密を全部見る必要があり、それが人のパスワードを見直すきっかけになった。アカウント・2段階認証・リカバリーコードの保管と、Mac の自動入力（Chrome、Touch ID で解錠）と iPhone の自動入力（Face ID で解錠）は済み。ほかの置き場から移すのは途中（iCloud の「パスワード」から 586 件を読み込み、振り分けではエージェント用の秘密は無かった。Chrome から 65 件を読み込み、振り分けでもエージェント用の秘密は無かった。Chrome の2つ目のプロファイルから 175 件を読み込み、振り分けでもエージェント用の秘密は無かった。移すと決めた3つのプロファイルのうち、残りの1つは移さないことにした。元の置き場をどうするかはまだ）。1週間の普段使いはまだ
