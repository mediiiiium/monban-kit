# Muse の回答：v1.5 の「出力から秘密の値を伏せる」への相談に答えて

作成日: 2026-11-13
相談：[muse-consult-redact-output.md](muse-consult-redact-output.md)
読んだもの：相談文書、`cmd/monban/run.go`（`syscall.Exec` で置き換わる現行の形）、[design.md](design.md) の「v1.5 の候補」と「正直に書くこと」

## 結論

- 作り方は案のとおりでよい。`exec` をやめて親として残る重さは、釣り合う（4-1）
- 切る口は作らない、に賛成。選べる形にすると、伏せない形が選ばれ続ける
- 完全一致だけ、に賛成（4-3）。短い値は「伏せずに通す」ではなく、実行を断る側を推す（理由は 4-3）
- 伏せた事実の門番ログへの申告は、v1.5 では後回しでよい。stderr の1行だけにする判断に同意する（4-4）
- 「これで防げないこと」の案はほぼ十分。足すものは 4-5 の3点

## 4-1. `exec` をやめて親として残ること

釣り合う、と読む。根拠は相談文書の読みのとおりで、1つ補強する。

- 値が同じ uid から見える場所は、現行でも子の環境変数（`ps eww`）が本命。`run` のメモリに値が増えても、見える相手（同じ uid のプロセス）は変わらない。守りの段（uid の分離）は動かない
- ただし正確に書くと、`run` のメモリの値は環境変数ではなくヒープの中身なので、`ps` では出ない。読むにはデバッガ的な接続が要り、macOS ではそれ自体に制約がある。つまり増える露出は「子の環境変数」という既存の露出より小さい
- 残る違いは時間のほう。現行は `exec` の瞬間に消えるが、親の形では子の実行時間だけ残る。長いコマンドほど残る時間が伸びる。これは 4-5 の「正直に書くこと」側に1行残すのがよい（下に案）

選べる形（許可リストの項目ごとに `exec`／親を選ぶ）には反対。理由は相談文書のとおり。対話のコマンドの逃げ道は、許可リストに入れないことで足りる（4-2）。

ついでに1つ。子の終わり方の返し方：案の「合図で死んだら 128＋番号」でも動くが、`exec` の形に寄せるなら、子が合図 S で死んだら `run` 自身が S を既定に戻して自分に送り直すほうが、呼び出し側（エージェントやシェル）から見た振る舞いが現行と一致する。実装が面倒なら 128＋番号でもよいが、その場合はシェルの表示（「終了コード 130」と「SIGINT で死んだ」）が変わることを、テストで確かめておくのがよい。

## 4-2. 端末を握るコマンド

- 「端末を握るコマンドは許可リストに入れない」と運用ルールに書けば足りる。門番を通すのは対話のないコマンド、という線引きは v1 の想定（Pushover 送信、API を1回叩く）と一致している
- 補助として、`run` の stdout が端末（tty）かどうかは起動時に分かる。エージェント経由の実行では普通パイプ側になる。ここで警告を出す必要はない。やるなら「stdout が端末なのに親の形で動く」場合に stderr へ1行出す程度。必須ではない
- `/dev/tty` への直接の書き込みは「防げないこと」に書くだけでよい。ファイル書き込み、ネットワーク送信と同じ棚（パイプを通らないものは伏せられない）

## 4-3. 一致の範囲

- 完全一致だけ、に賛成。変えた形（base64、URL エンコード、JSON のエスケープ、一部だけ）を広げるほど、「伏せてくれるはず」という思い込みを育てる。相談文書の読みのとおり
- 1つだけ実務の注記：値をそのまま `echo` するような素直な出力は、後ろに改行が付いても値そのもののバイト列は連続して現れるので、完全一致で拾える。拾えないのは、値の途中に何か（エスケープ文字、色付けの制御文字）が挟まった場合。これは 4-5 に入れる
- 短い値：8バイト未満は「伏せずに通して知らせる」ではなく、**実行を断る**側を推す。理由は安全ではなく出力の壊れ方。短くてありふれた値（数文字のトークンや "true" のような文字列）がコマンドの正常な出力の中に現れるたびに置き換わると、出力を静かに書き換えてしまう。伏せる処理の失敗は「値が見える」より「正しい出力が壊れて気づけない」ほうが始末が悪い。短すぎる秘密は作り直せることが多いので、断って理由（短すぎる）を返すのが正直。もちろん、実際に短い秘密を通す必要が出たら、そのときに閾値と扱いを見直せばよい

## 4-4. 伏せたことを残す場所

- stderr の1行は、そのまま残す。それ自体はエージェントの会話に出るが、出るのは「伏せた」という事実だけで値は出ない。むしろエージェント側が「そのコマンドは値を出す」と学習できる利益がある
- 門番のログへの申告は、診断情報としての価値はある（伏せが発生したという事実は、あとで人が見直すときに一番見たい種類の記録。申告制で黙らせることができても、その価値は大きくは減らない）。ただし **v1.5 では後回しでよい**、という進め方に同意する。理由は、申告は門番のプロトコルに新しい往復を足す変更で、伏せる仕組みそのものの完成とは別物だから。先に伏せる側を仕上げて、申告は独立した小さな段として後から足せる
- 後から足すときの門番側の条件は、この3つ＋印：①そのリクエスト ID を実際に門番が出したこと、②子の終了から短い時間（たとえば1時間）以内、③残すのは個数だけ、④ログの行に「run からの申告」と分かる印を付ける。監査の証明ではなく診断情報、と design 側に書く

## 4-5. 「これで防げないこと」に足すこと

案の4点は言いすぎも不足もなく、そのままでよい。足すなら次の3点。

1. **値の途中に何かが挟まった出力は一致しない。** 書き込みの境目で値が2つに割れただけのものは、末尾を手元に残す仕組みで拾える。でも、1文字ごとに色付けの制御文字を挟む、値の途中に改行や空白を挟んで出す、といった形になると、バイト列が連続しないので完全一致では拾えない。「境目で割れても拾う」と「間に何か挟まれば拾えない」は、混同されやすいので並べて書くのがよい
2. **親の形では、値が子の実行時間だけ `run` のメモリに残る。** 現行の `exec` の形では受け取った瞬間に消えていたものが、子が終わるまで残る。同じ uid から子の環境変数が見える前提は変わらないが、「消えるまでの時間」は正直に書く側の話として残す
3. **stderr の1行自体が情報になる。** 「出力から秘密の値を N か所伏せた」という通知は、そのコマンドが値を出したという事実を、エージェントを含む読み手に伝える。値そのものは守られるが、「伏せたかどうか」まで隠す仕組みではない。事故の記録としては必要な情報なので、隠す必要はない。ただ、防げることの範囲を書くときに、この1行が出る前提で書くのが正確

それと、案の最後の点（「盗もうとする相手は止めない」）は、この機能の位置づけとして一番大事な1行なので、削らずに残すのがよい。伏せるのは、事故やうっかりで出た値が会話やログに残るのを防ぐため、という目的の書き方も正確だと思う。

## 決まり（相談でも守る）

- 合言葉や本物のパスワードは、このリポジトリにも会話にも出さない。試すときの秘密はダミーの `MONBAN_TEST` だけ
- 「見せない」の効果を盛らない
