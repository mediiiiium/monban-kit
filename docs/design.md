## 一次経験（ここが出発点）

- パスワード管理が面倒。AIエージェントにも使わせたいが、渡し方が毎回手作業で怖い
- 複数のデバイス（Mac・Linux・Windows・スマホ）で使いたい
- AIは Claude に限らない（Codex、Gemini CLI など）

## 要件
- 金庫はクラウドでよい → Bitwarden（複数デバイス、エージェント向けの部品が一番揃っている）
- 原則：エージェントには必要な項目だけ、人の承認を経て渡す。「見せない」は効果を盛らずに書く

## 構成（見直し後）

```
人用の金庫      : Bitwarden 個人金庫（普段使い。エージェントは触らない）
エージェント用  : Bitwarden Secrets Manager（無料：マシンアカウント3・プロジェクト3・秘密は無制限）
                  ログイン情報は値にJSONを入れる規約で持つ（Notte の BitwardenVault の前例）
門番            : 許可リスト・代理実行・時間枠つき承認・キルスイッチ（mcp-warden の設計を借りる）
離れた場所      : Bitwarden Agent Access（ログインごとに人が承認。中継サーバーはセルフホスト推奨）
```

**途中で捨てた案と理由**

| 案 | 捨てた理由 |
|---|---|
| `bw serve` を常駐させ、その前に門番を置く | `bw serve` には認証がない。同じユーザーのエージェントは門番を通らずに全件取れる。別ユーザー＋Unixソケット（`--hostname unix:///パス`、CLI 2025.10.0〜。コードで確認）にすれば防げるが、Mac・Windows の導入が重い |
| `rbw` で高速化 | エージェントが `rbw get` を直接呼べるので門番を迂回される。Windows に触れていない。パスキーとDuoの2段階認証に対応していない |
| 公式 Bitwarden MCP をそのまま使う | 呼び出しごとに `bw` を起動するので遅い（`bw status` で約3.4秒）。パスワードをAIに返す。項目を絞る設定がない |

## 構成集に書くこと

- **2つのモード**：簡易＝同じユーザー＋門番＋承認（隔離ではなく事故防止だと明記）／厳格＝専用ユーザーかVM。Windows は WSL2 に寄せて Linux の手順に一本化する
- **承認**：
  - リスクで段を分ける。低リスクは時間枠つきの事前承認、高リスクは毎回の強い承認（Touch ID・Windows Hello・スマホ通知）
  - 承認画面には、エージェントの説明文ではなく門番が作った事実（項目・操作・宛先・コマンドのハッシュ）を出す
  - 承認はそのリクエストだけに使える1回限り・短命なものにする
- **「見せない」の段**：
  - A：承認後に値を返す
  - B：環境変数で注入する（モデルの文脈に残らないだけで、秘匿ではない）
  - C：代理実行（高価値の少数だけ）
  - ワンタイムコードは、シードではなく現在のコードだけを返す
- **無料枠での配分**（2026-11-10、公式の比較表で確認）：
  - 無料の上限は、マシンアカウント3つ・プロジェクト3つ・ユーザー2人。秘密の数は無制限
  - マシンアカウントは**1台に1つ**にする。エージェントごと（Claude Code・Codex・Gemini CLI・CI）に作ると、3つでは足りない。同じ台の中でどのエージェントかを見分けるのは、門番の許可リストとログで行う
  - 条件：合言葉（アクセストークン）は門番だけが持ち、エージェントには渡さない。エージェントが合言葉を読めると、門番を通らずに、そのマシンアカウントで読める秘密を全部取れる
  - イベントログと監査ログは有料（チーム、$6/ユーザー/月）からの機能。無料のまま使うなら、誰がいつ何を読んだかの記録は門番の側で持つ
- **失効手順**：パスワード変更・aac のペアリング解除・停止を1手順にまとめる
- **サプライチェーン**：中継サーバーのセルフホスト手順、bw と aac のチェックサム確認
- **門番の2系統**：個人金庫が背後＝otscup/secrets-broker／Secrets Manager が背後＝R055LE/secrets-broker（Linuxのみ）。otscup はライセンス表記が AGPL と MIT で食い違うので、同梱・改変するなら作者に確認する

## 門番の v1（2026-11-10 に Muse と相談して決めた）

相談と回答：[muse-consult-gatekeeper.md](muse-consult-gatekeeper.md)、[muse-consult-gatekeeper-response.md](muse-consult-gatekeeper-response.md)
作る順番：[v1-plan.md](v1-plan.md)

- **形**：薄い門番を自分で書く（案 B）。mcp-warden からは許可リストの書き方・時間枠つき承認・ハッシュ連鎖のログを、R055LE/secrets-broker からは別デバイス承認の段取りを借りる。コードは借りない
- **作り**：
  - Go の単一バイナリ。Mac の別ユーザー `_monban` で launchd のデーモンとして動かす。エージェントとは Unix ソケットだけで話す
  - 合言葉は `_monban` だけが読める 0600 のファイルに置き、`bws` には環境変数で渡す（引数では渡さない）。ログインしないユーザーのキーチェーンは実質使えないので、キーチェーンには置かない（2026-11-10 に Muse と相談して変更。[muse-consult-v1-plan-response.md](muse-consult-v1-plan-response.md)）
  - `bws` は子プロセスで呼ぶ。起動時に `bws` の署名（TeamIdentifier `LTZ2PFU5D6`）を確かめる
- **v1 に入れる**：読むだけ、許可リスト、ログ（`_monban` の持ち物にして、エージェントから書き換えられなくする）、キルスイッチ、コマンド単位の注入（`monban run`）、承認（Pushover で知らせ、判断はターミナルの `monban approve` / `deny`。Pushover は承認か拒否かを返せない）
- **v1 に入れない**：MCP、代理実行（段 C）、Touch ID のヘルパー（v2。LaunchAgent でログイン中のユーザーとして動かし、合言葉は持たせない）、Windows、ログイン情報の JSON 規約、**高リスクの秘密**（強い承認が付くまで門番に預けない）
- **v1.5 の候補**：
  - ~~注入先のコマンドの出力から秘密の値を探して伏せる~~ → 2026-11-13 に作った（[v1-plan.md](v1-plan.md) の「v1.5：出力から秘密の値を伏せる」。相談と回答：[muse-consult-redact-output.md](muse-consult-redact-output.md)、[muse-consult-redact-output-response.md](muse-consult-redact-output-response.md)）
  - 繋いできたのが本物の `monban run` かを、相手の pid の実行ファイル（置き場と署名）で確かめる。これで「申告したコマンド＝実際に動くコマンド」になる（エージェントがソケットへ直接書いて名乗る道が塞がる）。pid から実行ファイルのパスを取るのに libproc（cgo）が要るので v1 には入れない（2026-11-10 に Muse と相談。[muse-consult-allowlist-response.md](muse-consult-allowlist-response.md)）
- **正直に書くこと**：
  - 許可リストのエージェント欄は名札で、認証ではない（Claude Code も Codex も同じ uid）。守りの実体は uid の分離と承認
  - ターミナルの承認コマンドは、同じユーザーのエージェントが真似できる。事故防止であって、高リスクには使わない
  - キルスイッチは即時遮断ではない。門番を止めて合言葉を失効させても、最大1時間は読める
  - 同じ uid のエージェントは、門番を止められる（`monban stop`）。自分たちの作業への妨害はできるが、秘密は出ない。止めた事実は uid と pid つきでログに残る
- **変えない決まり**：マシンアカウントは Can read のまま。門番が乗っ取られても、秘密の書き換えや削除はできない
- **逃げ道**：別ユーザーで足りない高価値の秘密が出たら、Linux VM の中に門番を置く（R055LE がそのまま動く）

## 門番の v2：Touch ID の承認（2026-11-14 に Muse と相談して決めた）

相談と回答：[muse-consult-v2-touchid.md](muse-consult-v2-touchid.md)、[muse-consult-v2-touchid-response.md](muse-consult-v2-touchid-response.md)
実験の記録：[v2-experiments.md](v2-experiments.md)

ねらいは、高リスクの秘密を門番に預けられる承認を作ること。v1 の番号の承認は、同じ uid のエージェントもいるターミナルで打つので、高リスクには使わない。

### 形：Secure Enclave の鍵で、門番の問いに署名させる（案 B）

- 入れるとき、ヘルパーが Secure Enclave に署名の鍵（P-256）を作る。使うたびに生体認証が要る設定（`biometryCurrentSet`）で、データ保護キーチェーンに置く。鍵はチームとアクセスグループ（`<チームID>.<ヘルパーの bundle ID>`）に結び付く
- 承認のたびに、門番が1回限りの問いを作ってヘルパーに渡す。ヘルパーは中身を見せ、指が通ったら問いに署名して返す。門番は公開鍵で署名を確かめる（Go の標準ライブラリだけ）
- 強さは2層に分かれる。どちらも実測で立っている
  - **第1層：指なしでは署名が作れない。** 誰のプロセスから頼んでも、指が通らなければ Secure Enclave は署名しない。画面にパスワードへの逃げ道はなく、キャンセルは失敗になる（実験1）
  - **第2層：画面に出た中身への承認である。** 鍵を使えるのがヘルパーだけのときにだけ成り立つ。同じチームで署名した別のアプリはヘルパーのアクセスグループを名乗れるので（実験3）、**署名の身元をエージェントの手の届かない所に置くことで成り立たせる**（実験3c・3d）

### 署名の身元は、ビルド専用のユーザーにだけ置く

- 無料の Personal Team で署名する。profile は7日で切れるので、ヘルパーは毎週作り直す
- ビルドと署名は、通常のユーザー（管理者でない）`monban-build` で行う。Apple Development の身元と Xcode の Apple ID は、`monban-build` の側にだけ置く。エージェントの uid の側には、身元も Apple ID も置かない
  - 身元だけ消しても、Apple ID の入った Xcode があると戻ってくる（実験3c）。両方とも置かない
  - 証明書が `monban-build` の新しいものに変わっても、チームとアクセスグループが同じなら、前に作った鍵をそのまま使える（実験3d）。作り直しのたびに鍵を作り直す必要はない
- `monban-build` では monban のヘルパーだけをビルドする。同じチームで署名したアプリは、どれもヘルパーのアクセスグループを名乗れるため

### 毎週の作り直し（人の手順）

1. 前回ビルドしたコミットから今回までの、ヘルパーのソースの差分を人が読む。エージェントは作業中のリポジトリにも共有フォルダにも書けるので、ソースのすり替えはここでしか止まらない
2. `monban-build` でログインし、人が読んだコミットを、`monban-build` のホームの中に取ってきてビルドする。ビルドの作業フォルダは本人だけが開けるようにする（`chmod -R go-rwx`）
3. できたアプリを、`monban-build` が `/Users/Shared` にコピーする。`/Users/Shared` は置いた本人しか消したり差し替えたりできない（sticky）ので、エージェントは読めても置き換えられない
4. 人が自分のターミナルで sudo を打ち、`/usr/local/libexec/monban/`（root の持ち物）に入れる。LaunchAgent の plist は `/Library/LaunchAgents/`（root の持ち物）
5. どのユーザーの画面でサインインやビルドをしているかを確かめる。実験3d では、いつものユーザーの Xcode で間違えてサインインしかけ、エージェントの側に身元が戻った

### 承認の作り（回答の 4-1 をそのまま採る）

- **問いの中身**：領域名（`monban-approval-v2`）、128ビット以上の nonce、リクエストの ID、エージェントの名札、秘密の名前、コマンド全文のハッシュ、有効期限。門番は、自分が出した・まだ使っていない・期限内の問いへの署名だけを受ける
- **署名と公開鍵の形式**：公開鍵は X9.63 の生形式（65 バイト）、署名は X9.62 の DER、対象は問いのバイト列そのもの（ハッシュは両側で SHA-256）。門番は `ecdsa.ParseUncompressedPublicKey` と `ecdsa.VerifyASN1` だけで確かめる（実験4、`cmd/monban/touchid.go`）。問いのバイト列の並べ方は、ヘルパーを作るときに決める
- **ヘルパーの受け口**：繋いできた相手の uid が `_monban` でなければ断る
- **鍵は承認のたびに探し直す**：同じ鍵の参照を使い回すと、2回目は指なしで署名できた（実験1）
- **登録は儀式に閉じる**：鍵の作成と公開鍵の登録は、人のターミナル＋sudo で行う。公開鍵のファイルは root の持ち物で、門番は読むだけ。門番に公開鍵を差し替える口は作らない
- **同時に1件**：`touchid` の承認待ちは1件だけ
- **失敗は閉じる**：ヘルパーがいない・鍵がない・指が通らない・期限切れ・profile が切れて動かない、は全部断る。番号の承認やパスワードに落とす道は作らない
- **見せ方**：ヘルパーの自前の表示（エージェントの名札、秘密の名前、コマンドの全文、リクエストの ID、照合コード）と、システムの Touch ID 画面（理由文に同じ照合コード）の2枚。パスワードを打つ欄は自前の表示に出さない
- **許可リスト**：`"approval"` に `"touchid"` を足す。高リスクの秘密は `"touchid"` の項目だけにする

### 高リスクの秘密を預ける前に

- 実験5（ヘルパーへの入り込み）、実験6（鍵の失効と登録のやり直し）を済ませる。実験4（Go で署名を確かめる）は済んだ
- 2026-11-21 以降に、profile が切れた後の動きを確かめる。切れたヘルパーが鍵を使えなくなるなら、作り直しが遅れた間は `touchid` の承認が全部止まる（閉じる側に倒れるので、そのままでよい）
- **エージェントが作った偽のアプリが全部切れるのを待つ。** 実験3の `exp3other` はエージェントの側の身元で署名されていて、profile が切れる 2026-11-20 までヘルパーの鍵を使える。この日より前に、高リスクの秘密を `touchid` で預けない
- 申告どおりのコマンドが動くかは、v1.5 の候補（繋いできたのが本物の `monban run` か）が入るまで保証しない。この穴を受け入れて解禁するか、先に塞ぐかを、解禁のときに決める

### これで防げないこと

- root からは守れない（v1 と同じ）
- **ソースのすり替えは、人が差分を読む強さまでしか止まらない。** 読み飛ばせば、偽の中身に正規の署名が付く
- **身元がエージェントの側にあった間に作られた偽のアプリは、profile が切れるまで止まらない。** 身元を一度でもエージェントの側に戻せば、その日から7日間は第2層が落ちる
- 人が中身を読まずに指を当てれば、承認は意味がない。承認の疲れも防げない。同時1件と、`touchid` の項目を絞ることが、せめてもの歯止め
- 見た目を真似た偽の承認画面は防げない。照合コードで「見れば分かる」までは作るが、見なければ効かない
- Touch ID は「登録されている指のどれか」で、特定の人の指ではない
- 承認は「申告されたリクエスト」への承認で、実際に動くプロセスへの承認ではない
- 承認の後に値が渡る先は今までどおり注入先のコマンドで、同じ uid から見える。Touch ID で守るのは、渡すかどうかの判断
- ヘルパーを止める・殺すことは防げない（妨害）。秘密は出ず、止まった事実はログに残る
- 鍵の失効（指紋の追加・削除など）で `touchid` の秘密は全部止まる。復旧は登録の儀式だけ
