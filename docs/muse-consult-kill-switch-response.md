# Muse の回答：門番 v1 の8段目（キルスイッチ）

作成日: 2026-11-11
相談のメモ：[muse-consult-kill-switch.md](muse-consult-kill-switch.md)
1と2は、作った後の報告（会話）への答え。3は、相談のメモ（文面つき）への答え。

全体：作りは筋が通っている。止める要求の行を `kill` という別の印にしたことと、止まっているときも失効の手順を出して終了コード1にしたことは良い判断。

## 1. 同じ uid のエージェントが `monban stop` を打てる → 許してよい

- 理由は非対称性。「能力を減らす操作」は緩くてよい。間違って止めても秘密は出ず、困るのは自分たちの作業だけ
- 止めた事実は uid と pid つきでログに残るので、黙ってはできない
- 条件：design.md の「正直に書くこと」に、「同じ uid のエージェントは門番を止められる（自分の作業への妨害はできるが、秘密は出ない）」と1行入れる → 入れた

## 2. 9段目の起き直し → 「止めた印のファイル」が本体、`KeepAlive` は補助

- `KeepAlive` の `SuccessfulExit: false`（正常に終われば起き直さない）だけでは、再起動や再ログインで launchd が普通に起動してしまう。キルスイッチは「疑いが晴れるまで止まったまま」が本分なので、再起動をまたいで効く印のファイルが本体
- 印は、門番が自分の状態のディレクトリ（本番は `_monban` の 0700 の中）に置く。本番では、同じ uid のエージェントは消せない。解除は人が消す（解除の手順を書く）だけ
- 印の消し忘れで「起動しない」事故は、起動の失敗のメッセージに理由と解除の方法をはっきり出して防ぐ
- `KeepAlive`（落ちたら起き直す）は併用してよい。落ちたら直り、止めたら止まる、が両立する

## 3. 失効の手順の文面 → 言い過ぎはない。3点直す

- 手順の経路は、試用のときの実物と合っている。「漏れたと思うなら、秘密そのものも取り替える」の行は大事なので残す
- 先にもらった観点（失効させる場所、最大1時間は残ること、門番を止めるだけでは合言葉は失効しないこと、「完全に止まる」のような言い切りがないこと）は満たしている
- **止める前に渡した値は取り戻せない、を足す**。「まだ渡していない値は渡していない」だけだと、キルスイッチを信じすぎる。足す場所は確認の行ではなく、手順の冒頭の「止めても変わらないこと」に、合言葉が生きていることと並べる → 直した
- **「最大1時間」の主語をはっきりさせる**。Bitwarden の文書の主語は「ログイン済みのマシン」で、正規の門番に限らない。合言葉を盗んで先にログインした相手も同じ。「合言葉でログイン済みの相手は、誰であっても最大1時間は読み続けられる」にする → 直した
- **ただ止めただけのときに、合言葉を替えさせるのは重すぎる**。毎回重いと、読まれない手順になり、本当に漏れたときに効かない。2つに分ける → 直した
  - 漏れの疑いがない：合言葉のファイルはそのまま使える。起動し直すだけ（9段目からは、止めた印を消してから）
  - 漏れの疑いがある：失効 → 新しい合言葉 → ファイルの入れ替え → 起動

## 4. 止めた印の作り方（相談のメモの4）→ 異存なし

- 合図で止めたときや、落ちたときに印を置かないのも正しい（落ちたときは `KeepAlive` で起き直すのが仕事）

## そのほか

- 取り出し中の stop は、数秒待ってから答える偽の `bws` で再現できる、と勧められた → 試した（相談のメモの2）。子のプロセスが出力を握ったままだと門番が待たされる弱いところが見つかり、2秒で待つのをやめる形に直した
- 子のプロセスが出力を握ると待たされる癖は、止めるときだけでなく、普段の取り出しにもありうる。9〜10段目のどこかで、普段の道にも待ち時間の上限が効いているかを見る
  - 今の作り：2秒で待つのをやめる直しは、`bws` を動かすところ（`cmd.WaitDelay`）にあるので、普段の道の時間切れ（15秒）でも効く形。普段の道で試したことはまだない
