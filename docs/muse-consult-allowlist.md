## 1. ここまでの進み

- 1段目（骨組み）・2段目（ソケット）・3段目（`bws`＋最小のログ）を作り、人のターミナルで確かめた
- 3段目では、本物の合言葉（試用のもの）で `MONBAN_TEST` が取れた。値と合言葉は、ファイルのログにも門番の画面のログにも出なかった
- 今の要求の形は1行の JSON：`{"agent": 名札, "secret": 秘密の名前}`。返事は `OK …` か `NG 理由`。値はまだ渡していない（5段目で渡す）

## 2. 3段目で、相談せずに決めたこと（見てほしい）

1. **秘密の対応表**
   - `bws secret get` は ID でしか引けない。名前から引くのに `secret list` を呼ぶと、ほかの秘密の値まで全部門番に届く。だから「名前 ID」の対応表のファイルを持つことにした
   - 取れた秘密の名前（`key`）が、対応表の名前と違えば断る
   - 4段目で許可リストにまとめるつもり
2. **`bws` の置き場**
   - 署名（`anchor apple generic and identifier "bws" and certificate leaf[subject.OU] = "LTZ2PFU5D6"`）を `codesign --verify --strict` で確かめるのは起動時だけ
   - 確かめた後に差し替えられないよう、`bws` の本当の場所（シンボリックリンクをたどった先）と上のディレクトリが全部 root か門番自身の持ち物で、グループとほかの人から書けないことも確かめる。上のディレクトリが sticky（`/tmp` など）なら許す
   - 本番（`_monban`）では、`bws` を root の持ち物の場所に置く必要がある
3. **`bws` に渡す環境変数**
   - `BWS_ACCESS_TOKEN` と `HOME` だけ。`HOME` は合言葉のディレクトリ（0700）にした。`bws` の状態ファイルがその下にできる
4. **`bws` が失敗したときの出力**
   - `stderr` の最初の段落を、200 バイトまで門番の画面のログにだけ出す。ファイルのログには「bws が失敗」とだけ書く
   - `stderr` に値や合言葉が出ないことは確かめていない。出力の形を信じている

聞きたいこと：この4つで、穴や、もっとよい決め方はあるか。特に、`bws` の状態ファイルを合言葉と同じディレクトリに置くのはよいか。

## 3. 4段目で決めたいこと

### 3-1. 「どのコマンドに」を、門番は確かめられない

- 門番に繋いでくるのは `monban run`。`run` はユーザーの uid で動き、値を受け取った後で、コマンドを `exec` する
- だから要求の中の「コマンド」は、名札と同じく**申告**になる。同じ uid のエージェントは、`run` を使わずにソケットへ直接書けば、許可リストにあるコマンドを名乗って値を受け取れる
- そう考えると、コマンドの照合は事故防止（エージェントがうっかり別のコマンドに秘密を渡すのを止める）で、悪意のあるエージェントへの守りではない、と書くつもり

聞きたいこと：

1. この理解で合っているか
2. 申告より強くする安い手はあるか。考えたのは次の2つ。どちらも筋が悪いと思っている
   - 相手の pid の実行ファイルを門番が調べる → 繋いでくるのは `run` で、`exec` の前なので意味がない
   - 門番がコマンドを直接実行する → 前回「採らない」と決めた（門番に root が要る）
3. それでも v1 にコマンドの照合を入れる価値はあるか。6段目の承認で「どのコマンドに」を見せるには、要求の中にコマンドは要る

### 3-2. 要求の形

案：`{"agent": 名札, "secret": 秘密の名前, "command": [絶対パス, 引数…]}`

- `run` が `PATH` から引いて絶対パスにしてから送る（門番は `PATH` を信じない）
- 門番はこのコマンドを、照合・ログ・承認の表示に使う

聞きたいこと：

1. 引数まで送るべきか。送るなら、ログにどこまで書くか（引数に別の秘密が入っている心配）
2. 照合は「絶対パスの完全一致」だけでよいか、引数の決まった形（例：先頭が `api.example.com` に向く URL）まで見るべきか
   - 例えば `curl` を許すと、引数しだいで値をどこへでも送れる。パスだけの照合では、これを止められない
3. `sh`・`bash`・`env`・`python` のように、何でも実行できるコマンドは、許可リストに書けなくするべきか

### 3-3. 許可するコマンドの置き場

- 許可したパス（例：`/usr/bin/curl`）を、ユーザーが書き換えられる場所に置かれると、エージェントがそこに自分のスクリプトを置ける
- 案：門番は起動時に、許可リストの各コマンドについて `bws` と同じ確かめ（本当の場所と上のディレクトリが root か門番自身の持ち物で、グループとほかから書けない）をし、通らなければ起動しない
- 心配：本番では門番は `_monban` で動く。ユーザーのホームの下（`~/.local/bin` など）は、そもそも `_monban` から見えないことがある。見えても root の持ち物ではないので通らない。つまり許可できるのは、`/usr/bin` のような root の持ち物の場所だけになる。`/opt/homebrew` はユーザーの持ち物なので通らない

聞きたいこと：

1. この確かめは要るか。要るなら、Homebrew（`/opt/homebrew` はユーザーの持ち物）で入れたコマンドはどう扱うのがよいか
2. ただし 3-1 のとおりコマンドは申告なので、この確かめも事故防止の範囲を出ない。それでも入れるべきか

### 3-4. 許可リストのファイル

案：3段目の対応表を広げて、1つのファイルにまとめる。

```
# 秘密の名前   ID                                     許可するコマンド（絶対パス）   名札（* はだれでも）
MONBAN_TEST    00000000-0000-0000-0000-000000000000   /usr/bin/printenv             *
```

- 1秘密に複数のコマンドや名札を許すときは、同じ名前の行を重ねる（ID は同じでなければ起動しない）
- 形は、Go の標準ライブラリだけで読めるもの（この行の形か JSON）にしたい。TOML や YAML は外のライブラリが要る

聞きたいこと：

1. この行の形でよいか、JSON のほうがよいか。引数の形まで書くなら、行の形では足りないかもしれない
2. 名札の欄は要るか。名札は認証ではないが、ログと事故防止（Codex には渡さない、など）には使える
3. 持ち主は `_monban` と root のどちらがよいか
   - root：`_monban` が乗っ取られても、許可リストは書き換えられない。直すたびに `sudo` が要る
   - `_monban`：門番と同じ持ち主。門番が読み書きの両方をできてしまう
   - 今は試すときに門番を自分の uid で動かしているので、「root か門番自身の持ち物で、グループとほかから書けない」を確かめている（対応表と同じ）
4. 変えたときに読み直すか、門番を起動し直すか。v1 は起動し直すだけにするつもり

### 3-5. 断るときの返事

- 今は理由を返している（`NG 対応表にない秘密` など）
- 許可リストで断るとき、「秘密がない」と「秘密はあるが、このコマンドには許していない」を分けて返すと、エージェントに許可リストの中身を探られる

聞きたいこと：返事は分けないほうがよいか（ログにだけ詳しい理由を書く）。

## 決まり（相談でも守る）

- 合言葉や本物のパスワードは、このリポジトリにも会話にも出さない。上の例の ID は作り物
- 「見せない」の効果を盛らない
