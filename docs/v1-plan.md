# 門番 v1 の作り方（順番）

作成日: 2026-11-10
前提：[design.md](design.md) の「門番の v1」、[pre-v1-experiments.md](pre-v1-experiments.md) の結果（別ユーザーの環境変数は `ps eww` で見えない、`get` は約0.5秒）

## 決まり

- 合言葉や本物のパスワードは、このリポジトリにも会話にも出さない。試すときの秘密はダミーの `MONBAN_TEST` だけ
- 1段ずつ作り、段ごとに「動いた」を人の目で確かめてから次へ進む
- 「見せない」の効果を盛らない。段ごとに「これで防げないこと」も書く

## 先に確かめること（コードを書く前）

| 確かめること | なぜ要るか |
|---|---|
| ログインしないユーザー（`_monban`）の launchd デーモンから、キーチェーンを読めるか | デーモンのユーザーにはログインのキーチェーンが開いていないかもしれない。読めなければ、合言葉の置き場（`_monban` だけが読めるファイルなど）を考え直す |
| Unix ソケットの相手の uid を、macOS で Go から取れるか（`LOCAL_PEERCRED` / `getpeereid`） | 許可リストとログの「誰から」の土台 |
| Pushover で「承認／拒否」を返せるか | 送るだけなら簡単。緊急の優先度の「受領確認」は「見た」しか返さず、「拒否」がないかもしれない |
| Go を入れる | このマシンにまだない |

## 作る順番

1. **骨組み**：`monban` という1つのバイナリに、`daemon`・`run`・`approve`・`stop` の入口だけ作る。中身は空
2. **ソケット**：`daemon` がソケットを開き、`run` が繋いで、相手の uid をログに出す。ソケットは `_monban` の持ち物にし、使う人だけが繋げる権限にする
3. **`bws` を呼ぶ**：`daemon` が `bws secret get` を子プロセスで呼ぶ。`bws` は絶対パスで呼び、起動時に署名（TeamIdentifier `LTZ2PFU5D6`）を確かめる。合言葉は環境変数で渡す
4. **注入**：`monban run MONBAN_TEST -- コマンド` で、値をそのコマンドのプロセスにだけ渡す。値は `daemon` から `run` へソケットで渡り、`run` が環境変数に入れて `exec` する
5. **許可リスト**：どの秘密を、どのコマンドに渡してよいか。ファイルは `_monban` か root の持ち物にし、エージェントから書き換えられなくする
6. **承認**：最初はターミナルの承認コマンド（事故防止）。次に Pushover
7. **ログ**：誰が・いつ・どの秘密を・どのコマンドに。`_monban` の持ち物にし、ハッシュの連鎖で書き換えを見つけられるようにする
8. **キルスイッチ**：`monban stop` で門番を止め、合言葉の失効の手順を出す（失効しても最大1時間は読める、と書く）
9. **本番の形でもう一度確かめる**：launchd のデーモン・`_monban`・`bws` で、実験1（`ps eww` で合言葉が見えないか）をやり直す

## これで防げないこと（v1）

- 4で `run` が受け取った値は、ユーザーの uid の中にある。注入先のコマンドが値を出力すれば、エージェントの会話に残る（伏せる処理は v1.5）
- 許可リストのエージェント欄は名札で、認証ではない
- ターミナルの承認コマンドは、同じユーザーのエージェントが真似できる。だから v1 は高リスクの秘密を扱わない
- エージェントが `sudo` を取れれば、全部守れない（モデルの外）
