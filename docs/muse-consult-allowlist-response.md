# Muse の回答：門番 v1 の4段目（許可リスト）と、3段目で決めたこと

作成日: 2026-11-10
相談のメモ：[muse-consult-allowlist.md](muse-consult-allowlist.md)
Muse の回答を、相談の「聞きたいこと」の順にまとめた。末尾の「未確認」は、Muse が書いたがまだ確かめていない点。

## 2. 3段目で決めた4つ

1. **秘密の対応表** → このままでよい
   - `secret list` を呼ぶと、要求されていない秘密の値まで門番に届く。対応表で `get` だけに絞るのが筋
   - 取れた `key` を対応表と照らすのも、対応表と実物のずれを見つけられるのでよい
   - 秘密を作り直すと ID が変わるので、対応表を直して門番を起動し直す。v1 の「起動し直して読み直す」と揃っている
2. **`bws` の置き場** → このままでよい
   - 署名は起動時だけ、その代わりに本当の場所と上のディレクトリの持ち主と書き込みを見る、という組み立ては健全
   - sticky なディレクトリを許すのも正しい（持ち主のほかは消せず、上書きもファイルの権限で止まる）
   - 知っておくこと：起動の後に正しい手順で `bws` を新しくすると、門番は起動し直すまで、新しい実物を署名を確かめずに呼ぶ。ただ書けるのは root の持ち物の場所だけなので、守りの前提の内側。起動し直すときに確かめ直す今の形で足りる
3. **状態ファイルと合言葉を同じディレクトリに置く** → 害はない
   - 守りの境はファイルではなくディレクトリ（0700・`_monban` だけ）。状態ファイルに合言葉と同じくらいの情報が載るとしても、同じ境の中なら見える人は増えない
   - 困るのは実務だけ。`bws` が作るファイルと合言葉のファイルが混ざると、起動時の確かめや棚卸しで「あるはずのもの」がぼやける
   - 気になるなら、`HOME` を合言葉のディレクトリの下の専用の子ディレクトリ（同じく 0700）にし、合言葉の置き場は「ファイル1つだけ」と決める。余計なものが増えたら気づける。必須ではない
4. **`bws` の `stderr`** → いちばん気になる
   - 画面のログは、launchd を通すとファイルに残ることもある
   - 安い手1：門番は合言葉と、取った後なら秘密の値を知っている。出す前に、その文字列があれば伏せる。完全一致の置き換えだけなので十数行で書ける。「出力の形を信じる」から「知っている秘密は必ず伏せる」に上がる。後の「出力の伏せ処理」の先取りにもなる
   - 安い手2：本番では生の `stderr` を出さない。失敗の分類（認証・通信・見つからない・その他）と終了コードだけにし、生の出力は開発のときだけの指定の後ろに置く。自分の uid で試している今は生でもよいが、本番の形にするときに切り替える

## 3-1. 「どのコマンドに」は申告か

1. **理解は合っている**
   - 同じ uid である限り、門番が受け取るのは「その uid の、何かのプロセスからの接続と、JSON の主張」だけ。`exec` の後に何が走るかは、もともと確かめられない
   - コマンドの照合の役目は、事故防止・承認の画面の材料・ログの材料の3つ。悪意への守りではない
2. **申告より強くする手**
   - 相手の pid の実行ファイルを調べる案は、「意味がない」は半分だけ正しい
     - 調べるのは「これから `exec` するコマンド」ではなく、「今繋いでいるのが本物の `monban run` か」
     - 本物の `run` は、自分の引数をそのまま要求に書き、その引数を `exec` する（嘘をつかない）。繋いできたのが本物の `run` だと確かめられれば、エージェントがソケットへ直接書いて名乗る道が塞がり、「申告したコマンド＝実際に動くコマンド」になる
     - `bws` と同じく、置き場（root か門番の持ち物の場所）と署名で縛るのが前提
     - ただし強くなるのは「コマンドの表示が正直になる」ことだけ。エージェントが本物の `run` で `sh -c 何でも` を選ぶことは止められない（3-2 の話）
     - pid から実行ファイルのパスを取るには libproc（cgo）が要り、標準ライブラリだけという方針とぶつかる。v1 は申告のままにし、この強化は v1.5 の項目として design に残すのが釣り合う。v1 の承認はターミナルなので、正直さの足りなさは人が画面を見て補える
   - **今すぐ入れる細部**：`run` は値を受け取ったら、コマンドを `exec` する前にソケットを閉じる。開いたまま `exec` すると、注入先のコマンドが門番への接続を引き継ぐ。Go の `net` は初めから close-on-exec だが、明示して閉じる前提で作り、v1 の「`run` で守ること」に1行足す
3. **それでも v1 に入れる価値はある**
   - 上の3つの役目に加え、「この秘密はこのコマンドにだけ」の組み合わせを間違える事故は、実際に起きやすい

## 3-2. 要求の形

1. **引数まで送る** → 賛成。承認とログに要る。門番が見えないものは、人も判断できない
   - ログにどこまで書くか：引数には別の秘密が入りうる（`curl -H "Authorization: Bearer …"` の形）
     - (a) 承認の画面には全部出す。ファイルのログには引数の数と、全体のハッシュを残し、全文は残さない
     - (b) 少なくとも、今回の秘密の値と完全に一致する部分は伏せる（2-4 と同じ仕組み）
     - v1 は (a)＋(b) で足りる。あわせて「引数に秘密を埋めるコマンドは、許可に向かない」と書く
2. **照合の細かさ** → 絶対パスの完全一致が基本。引数の形まで見るのは例外
   - 一般の「引数の決まりの言語」は v1 には多すぎる
   - 例外は1種類だけ：`curl` のように「どこへでも送れる」コマンドに、送り先のホストの許可を付けられるようにする（URL らしい引数のホスト名が、許可リストのホストと一致すること）。これで `curl` の実用上の穴の大半が塞がる
3. **何でも実行できるコマンド** → 書けなくする
   - `sh`・`bash`・`zsh`・`env`・`python`・`perl`・`ruby`・`node`・`osascript` などは、門番の側に固定の拒否の一覧を持ち、許可リストに書かれていたら起動しない
   - これらを許すと、「コマンド」という考え自体が崩れる
   - スクリプトを動かしたいときは、そのスクリプトのファイルのパスをコマンドとして書く形に寄せる（スクリプトの中身は、持ち主が書けるものという前提を文書に書く）

## 3-3. 許可するコマンドの置き場

1. **入れるべき**
   - コマンドが申告でも、「申告された絶対パスにある実物が本物か」は別の話。確かめがないと、許可リストの絶対パスが、ユーザーの書き換えられる場所では意味を持たない
   - `bws` 用の確かめ（`checks.go`）をそのまま使えるので、費用も小さい
2. **Homebrew** → 初めは厳しく（root か門番の持ち物の場所だけ）、例外は許可リストの項目ごとに明示する
   - 例外の印を付けた項目（`/opt/homebrew/...`）は起動を止めない。ただ、起動時の画面とログに「ユーザーの持ち物の場所のコマンドを許している」と出す。承認の画面でも、その項目に弱いことを示す印を付ける
   - こうすると例外は「知らないうちに緩んでいる」ではなく、「本人が選んだ緩さ」として残る
   - `/usr/bin/curl` のように OS のもので足りるものは OS のものを使い、Homebrew にしかないもの（`gh` など）だけを例外にする

## 3-4. 許可リストのファイル

1. **JSON がよい**
   - 引数の例外（送り先のホスト）を書く欄が要るので、行の形では窮屈
   - Go の標準ライブラリ（`encoding/json`）で読める。要求とログも JSON なので、形が1種類に揃う
2. **名札の欄は要る**
   - 認証ではないが、事故防止（「この秘密は Codex には渡さない」という人の意図を書ける）と、ログと承認の画面の読みやすさに効く
   - 「名札は認証ではない」と書いた上で残す
3. **持ち主は root**
   - 門番（`_monban`）が自分の許可リストを書き換えられると、門番が乗っ取られたときに、自分で許可を広げられる
   - root の持ち物の 0644 にする（中身に秘密の値はないので、読めるのは構わない）。直すときだけ `sudo` を使う
   - 試すときに自分の uid で動かす間は、「自分か root」を許す今の確かめでよい。ただ本番の決まりは root と書く
4. **読み直しは、起動し直すときだけ** → 賛成。v1 はそれで足り、起動し直す費用も小さい

## 3-5. 断るときの返事

- **分けないほうがよい**
  - 返事は一律に `NG`（と、人がログと照らすためのリクエストの ID）だけにし、詳しい理由は門番のログにだけ書く
  - 分けて返すと、ソケットに書ける同じ uid のプロセスが、秘密の名前と組み合わせを総当たりで探れる
  - 承認の結果も同じで、「拒否された」「時間切れ」「許可リストにない」は、`run` の側では1つの `NG` にまとめる
  - 使う側の不便は、`run` が「理由は門番のログを見てください」と添えれば足りる

## まとめ（Muse のおすすめ）

4段目は、次の形で組む。

- JSON の許可リスト（秘密の名前・ID・コマンドの絶対パス・あれば送り先のホスト・名札）
- 持ち主は root
- 何でも実行できるコマンドは、固定の一覧で断る
- 置き場の確かめは `bws` のものを使い回す。例外は明示する
- 断るときの返事は一律

## 未確認（Muse の回答のうち、まだ確かめていないこと）

- ~~Go の `net` のソケットは、初めから close-on-exec になっている~~ → 確かめた。go1.27.3 の `src/net/sys_cloexec.go`（`darwin` 向け）が、ソケットを作るたびに `syscall.CloseOnExec` を呼んでいる（2026-11-10）。それでも `run` は `exec` の前に明示して閉じる
- pid から実行ファイルのパスを取るには libproc（cgo）が要る（標準ライブラリや `golang.org/x/sys/unix` だけでは取れない）
- `curl` の「送り先のホストの許可」で、`curl` の実用上の穴の大半が塞がる（`curl` の URL の読み方は、Go の `net/url` と同じとは限らない。プロキシや設定ファイルの指定もある）
- launchd の画面のログ（`stderr`）は、plist の指定しだいでファイルに残る
