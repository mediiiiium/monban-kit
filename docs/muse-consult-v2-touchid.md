## 1. なぜ今これか

- v1（10段）と v1.5（出力から秘密の値を伏せる）は、本番の形で動いている。通している本物の秘密は Pushover のトークン（低リスク）1本だけ
- v1 は高リスクの秘密を扱わない。承認が強くないから。番号はスマホと Pushover を通り、人が打つのは同じ uid のエージェントもいるターミナル
- v1.5 の相談では「高リスクの秘密を預けたい場面がまだ来ていないので、v2 は後でよい」と書いた。これは間違いだった。強い承認がない限り高リスクの秘密は預けられないので、門を作らない限り、その場面はいつまでも来ない。「困った順に作る」が効くのは細かい機能で、前提になる門には効かない
- だから v2 を本丸として進める。ねらいは、高リスクの秘密を門番に預けられる承認を作ること

## 2. 先に気づいたこと：Touch ID を出すだけでは強くならない

- ヘルパーはログイン中のユーザー、つまりエージェントと同じ uid で動く。門番がソケットの相手で分かるのは uid と pid まで
- だから、ヘルパーが門番に「Touch ID が通った」と返すだけの形だと、エージェントが同じソケットに繋いで「通った」と返せる。ヘルパーを止めて、偽のヘルパーを置くこともできる
- つまり問いは「Touch ID を出せるか」ではなく、**門番が「人の指で承認された」をどう確かめるか**。ここが崩れると、v1 の番号より弱くなりうる（番号は少なくとも、エージェントから見えない）

## 3. こう作るつもり（案）

### 3-1. 形の候補

**案 A：ヘルパーの返事を、相手の実行ファイルで信じる**
- ヘルパーは LocalAuthentication で Touch ID を出し、結果（はい・いいえ）を門番に返す
- 門番は、繋いできた pid の実行ファイルの置き場（root の持ち物）と署名を確かめてから、返事を受ける
- pid から実行ファイルを取るのに libproc（cgo）が要る。v1.5 の候補「本物の `monban run` かを確かめる」と同じ部品
- 気になるところ：同じ uid のプロセスが、署名済みのヘルパーのプロセスに入り込めるか（デバッガのような接続、ライブラリの差し込み）。Hardened Runtime で塞がるか

**案 B：Secure Enclave の鍵で、門番の問いに署名させる**（こちらを推したい）
- 入れるとき、ヘルパーが Secure Enclave に署名の鍵を作る。使うたびに生体認証が要る設定（`biometryCurrentSet`）にする。公開鍵は、root の持ち物のファイルに置いて門番が読む
- 承認のたびに、門番が1回限りの問い（乱数＋リクエストの ID・秘密の名前・コマンドのハッシュ）を作ってヘルパーに渡す。ヘルパーは Touch ID の画面に中身を出し、指が通ったら問いに署名して返す
- 門番は公開鍵で署名を確かめる。ECDSA P-256 なので、門番の側は Go の標準ライブラリ（`crypto/ecdsa`）だけで足りる
- この形だと、ソケットに誰が繋いでも構わない。署名を作れるのは鍵を使えるものだけで、鍵を使うたびに指が要る
- 気になるところ：
  - 鍵を使えるのは、鍵を作ったヘルパーだけか。同じ uid の別のプログラムが、同じ鍵で署名を頼めるか（キーチェーンのアクセスの決まりが、コード署名に結び付くか）
  - そのために、Apple の開発者の登録（有料）と署名が要るか。自分で作った署名（ad-hoc）でも足りるか

**案 C：別のデバイスで承認を返す**
- スマホで承認し、その結果を門番に返す。Pushover は承認・拒否を返せないので、別の仕組みが要る
- 外のサービスに頼る部分が増えるので、案 B が成り立つなら、こちらは選ばないつもり

### 3-2. 案 B で決めておきたいこと

- **ヘルパーの言語**：Swift で書く（LocalAuthentication と Security を素直に呼べる）。門番は Go の標準ライブラリだけのままにする。ヘルパーは別のバイナリ
- **置き場**：ヘルパーのバイナリは `/usr/local/libexec/monban/` に置く（root の持ち物）。LaunchAgent の plist は `/Library/LaunchAgents/` に置く。`~/Library/LaunchAgents/` はユーザーが書き換えられるので使わない
- **許可リスト**：`"approval"` の欄に `"touchid"` を足す。高リスクの秘密は `"touchid"` の項目だけにする
- **代わりの道はない**：Touch ID が使えないとき（蓋を閉じて外付けのキーボードを使っている、指が通らない）は断る。番号の承認やログインのパスワードには落とさない。パスワードに落とすと、`osascript` で打つ道が開くため
- **画面に出すもの**：エージェントの名札、秘密の名前、コマンドの全文、リクエストの ID。中身は門番から来たものだけを出す

### 3-3. 最初にする実験

作る前に、案 B が成り立つかを小さく確かめたい。

1. LaunchAgent で動かした Swift のヘルパーから、Touch ID の画面を出せるか
2. Secure Enclave に `biometryCurrentSet` の署名の鍵を作れるか。ad-hoc の署名でも作れるか、開発者の登録が要るか
3. 同じ uid の別のプログラムから、その鍵で署名を頼めるか（頼めないことを確かめたい）
4. ヘルパーが作った署名を、Go の標準ライブラリで確かめられるか

## 4. 聞きたいこと

### 4-1. 案 A・B・C のどれか

- 案 B を推したい。理由は、門番の側に cgo が要らず、ソケットの相手を信じなくてよいから
- 見落としている弱さはあるか。特に、鍵がヘルパーだけに結び付くかどうか

### 4-2. 同じ uid のエージェントにできること

案 B で、エージェントに次のことができるかを知りたい。

- 偽の Touch ID の画面を出して、人に別の承認をさせる（本物の画面の文言をまねる）
- 本物のリクエストが来て人が待っているときに、自分の頼みを割り込ませて、指を当てさせる
- ヘルパーを止めて、承認を全部断る形にする（妨害。秘密は出ないので、v1 の `monban stop` と同じ棚でよいと読んでいる）

### 4-3. 開発者の登録

- Secure Enclave の鍵をヘルパーだけに結び付けるのに、有料の登録が要るなら、払う価値はあるか
- 要らない形があるなら、それで何が弱くなるか

### 4-4. 実験の順番

- 3-3 の4つで足りるか。先に確かめるべきことはあるか

### 4-5. 「これで防げないこと」に書くこと（案）

- root からは守れない（v1 と同じ）
- 人が画面を読まずに指を当てれば、承認は意味がない。画面の中身は門番から来たものだけれど、コマンドが申告どおりかは、v1.5 の候補（相手の実行ファイルで確かめる）が入るまで保証しない
- 承認の後に値が渡る先は、今までどおり注入先のコマンドで、同じ uid から見える（子の環境変数）。Touch ID で守るのは「渡すかどうかの判断」で、渡した後の値ではない
- 足りない、言いすぎ、のところがあれば教えてほしい

## 決まり（相談でも守る）

- 合言葉や本物のパスワードは、このリポジトリにも会話にも出さない。試すときの秘密はダミーの `MONBAN_TEST` だけ
- 「見せない」の効果を盛らない
