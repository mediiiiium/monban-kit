# Muse の回答：門番 v1 の作る順番と、コードの前に確かめること

作成日: 2026-11-10
相談のメモ：[muse-consult-v1-plan.md](muse-consult-v1-plan.md)
Muse の回答を、相談の「聞きたいこと」の順にまとめた。末尾の「未確認」は、Muse が書いたがまだ確かめていない点。

## 0. 実験の結果について

- OS に入っているプログラムの環境変数が、同じユーザーからでも見えなかった件の理由：`ps` が環境変数を読む道（`KERN_PROCARGS2`）は、Apple が署名したプラットフォームのバイナリに対して、カーネルの側で止められているからだろう
- 大事なのは、そこから言えること。見えるかどうかは、uid だけでなく**バイナリの署名の性質**にもよる
- 自分で作る Go のバイナリは、「署名し直した複製」と同じ側になる。だから本番の形でもう一度確かめる段は、この意味でも要る

## 1. `_monban` のキーチェーン → 使わない。0600 のファイルに置く

- ログインしないユーザーのログインのキーチェーンは、実質的に使えない
  - キーチェーンが開くのはログインのときだけ
  - デーモンからプログラムで開けようとすると、「開けるためのパスワードをどこに置くか」という同じ問題が一段下で起きる
- 代わりの置き場：
  - `_monban` だけが入れる 0700 のディレクトリの中に置く。ファイルも `_monban` の持ち物で 0600
  - デーモンは起動時に1回だけ読んでメモリに持ち、ほかには書かない
  - これで読めるのは root と `_monban` だけになり、守りの前提と一致する。`/etc` の下に 0600 で置くのは、普通のデーモンの作法でもある
  - 電源が切れているときの暗号化は FileVault に任せる、と割り切る
- System キーチェーンは、デーモン向けの正統な仕組み。ただ項目の許可がバイナリの署名に結びつくので、署名し直すたびに壊れる。署名が固まってから考え直す
- この判断で、「先に確かめること」のキーチェーンの実験は要らなくなる

## 2. Pushover → 「承認／拒否」は返せない。知らせるだけに使う

- Pushover は基本的に一方向の通知
  - 緊急の優先度（priority=2）の受領確認は「見た」だけで、承認か拒否かは返せない
  - メッセージに付けられるのは URL のリンクまで。Telegram のようなボタンと折り返しの仕組みはない
- v1 の形：
  - Pushover は知らせるだけ。「どのエージェントが・どの秘密を・どのコマンドに」とリクエストの ID を送る
  - 判断はターミナルで行う：`monban approve <ID>` / `monban deny <ID>`
- スマホだけで済ませたくなったときの道（待ち受けを増やさない）：
  - iOS のショートカットから SSH：Tailscale 経由で Mac に SSH して `monban approve` を打つ。待ち受けは今ある sshd だけ、認証は SSH の鍵。個人用では一番増える面が少ない
  - Telegram のボタン＋ロングポーリング：otscup/secrets-broker の前例。デーモンから外へ取りに行くので待ち受けは増えない。ただ Telegram に頼ることになる

## 3. ソケットの相手 → `getpeereid` で足りる。ディレクトリの権限に注意

- `LOCAL_PEERCRED`（`golang.org/x/sys/unix` の `GetsockoptXucred`）で、繋いできたプロセスの uid が取れる
  - わかるのは uid まで。エージェントの見分けにはならない（前回のとおり）
  - 役目は「許可した uid 以外を締め出すこと」と「ログの『誰から』を確かにすること」。それなら足りる
- 穴になりやすいのは、ソケットのファイルより**置き場のディレクトリ**
  - ディレクトリ：`_monban` の持ち物。グループは使う人だけが入る専用のグループ。モードは 0750（グループに書き込みを付けない）
  - ソケット：`_monban` の持ち物、同じグループ、0660
  - ディレクトリにグループの書き込みを許す（0770）と、ユーザーのプロセスがソケットを消して、偽の門番に差し替えられる。偽物は本物の秘密を出せないが、要求の中身（秘密の名前とコマンド）を記録したり、邪魔したりはできる
- デーモンの側でも、繋いできた uid が設定に書いた持ち主の uid と一致するかを照合する（グループの入り方の緩さに頼らない）
- 起動時に、ディレクトリとソケットの持ち主とモードを調べ、想定と違えば起動しない

## 4. 注入の値の通り道 → この形でよい

- デーモン（`_monban`）→ ソケット → `run`（ユーザーの uid）→ 環境変数 → `exec`、は段 B として正しい
- 残るのは、注入先のコマンドの環境変数が同じ uid から `ps eww` で見えること。これは段 B の性質として書いてある範囲
- `run` で守ること：
  - 値は引数にもファイルにも置かず、受け取ったらすぐ `exec` する（プロセスが入れ替わるので、`run` のメモリに値が残り続けない）
  - エラーやデバッグの出力にも値を出さない
  - 値はリクエスト1回限り。使い回さない
- 「デーモンがコマンドをユーザーの権限で直接実行する」形は採らない。デーモンに root が要り、守るものより門番の権限のほうが大きくなる

## 5. 順番 → 2か所を入れ替え、1段を足す

- **注入と許可リストを入れ替える**。今の順だと、最初に動く形が無防備になる。要求の形（どのエージェントが・どの秘密を・どのコマンドへ）に許可リストで要る項目が全部入っている必要があるので、先に許可リストを通すほうが、やり取りの形が歪まない
- **ログを2つに分ける**。最小の記録（時刻・繋いできた uid・申告されたエージェント名・秘密の名前・結果を1行ずつ足す）は、秘密が初めて動く「`bws` を呼ぶ」段でファイルに出す。ハッシュの連鎖は後の段のままでよい
- **常駐化の段を足す**（本番の形で確かめる段の前）：`_monban` ユーザーの作成、LaunchDaemon の plist、ディレクトリと権限、合言葉のファイルの配置、入れ方と消し方
- キルスイッチは今の位置のままでよい

まとめた順番：骨組み → ソケット → `bws`＋最小のログ → 許可リスト → 注入 → 承認 → ログのハッシュ連鎖 → キルスイッチ → 常駐化 → 本番の形で実験1をやり直す

## 未確認（Muse の回答のうち、まだ確かめていないこと）

- System キーチェーンの項目の許可は、署名し直すたびに壊れる
- Pushover には、承認か拒否かを返す仕組みがない（ボタンや折り返しがない）
- `GetsockoptXucred` で、繋いできたプロセスの uid が macOS で取れる
