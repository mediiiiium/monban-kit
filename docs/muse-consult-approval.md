読んでほしいもの：[v1-plan.md](v1-plan.md)（5段目までの「決めたこと」「これで防げないこと」と、6段目）、`cmd/monban/` のコード

## 1. ここまでの進み

- 4段目（許可リスト）と5段目（注入）を作り、本物の合言葉（試用のもの）で人のターミナルで確かめた
- 今は、許可リストを通った要求には、すぐ値を渡している。`run` は値を環境変数（秘密の名前）に入れ、ソケットを閉じてから、送った絶対パスを `exec` する
- 決まっていること：Pushover は知らせるだけ。判断はターミナルの `monban approve <ID>` / `monban deny <ID>`。承認・拒否・時間切れは、`run` には同じ `NG` で返す。ターミナルの承認は、同じ uid のエージェントが真似できる（事故防止。高リスクの秘密は扱わない）

## 2. 案（こう作るつもり）

### 2-1. 流れ

1. 門番は、許可リストを通った要求を「待ち」にし、Pushover で知らせる。`run` との接続は開いたまま待たせる
2. 人がターミナルで `monban approve <承認の番号>` を打つ。`approve` も同じソケットに繋ぎ（uid の照合も同じ）、`{"op":"approve","code":…}` を送る
3. 門番は、承認されたら `bws` で取り出して渡す（取り出すのは承認の後。拒否や時間切れなら、値は門番にも届かない）
4. 拒否・時間切れ・`run` が先に切れた、はどれも待ちから外してログに残す。`run` への返事は `NG <リクエストの ID>`

### 2-2. 承認の番号を、リクエストの ID と分ける

- いまのリクエストの ID は `run` にも返している（ログと照らすため）。これで承認できると、エージェントは自分の要求の ID を知っているので、`monban approve <ID>` を自分で打てる
- 案：承認には、別の「承認の番号」を使う。番号は Pushover と門番の画面のログにだけ出し、`run` には返さない
  - 本番（`_monban`）では、門番の画面のログはユーザーの uid から読めない。番号を知る道はスマホだけになる
  - エージェントは、番号を当てるか、人が打った `monban approve` の後の痕跡（シェルの履歴など）を見るしかない。番号は1回限りなので、後から見ても使えない
  - 番号の形：人が打つので短くしたい。案は 8 桁の数字（約 27 ビット）。外れの番号を3回送られたら、待っている要求を全部断る（総当たり止め）
- これで「同じ uid のエージェントが真似できる」は、「番号を当てるか、スマホを見ない限り真似できない」まで上がると思う。ただ試すとき（自分の uid で動かす）は、画面のログが読めるので上がらない

### 2-3. 承認の画面

- `monban approve <番号>` は、まず門番から要求の中身（門番が作った事実）を受け取って表示し、`y` を打ったら承認する
  - 出すもの：名札・秘密の名前・コマンドの絶対パス・引数の全文（今回の秘密の値と一致する部分は伏せる。ただ値は承認の後に取るので、この時点では伏せられない → 3-3）・`userOwned` の印・繋いできた pid
- `monban deny <番号>` は確かめずに断る

### 2-4. Pushover

- 送るもの：承認の番号・名札・秘密の名前・コマンドの絶対パス・引数の数。引数の全文は送らない（外のサービスに別の秘密が出るかもしれない）
- Pushover のアプリのトークンとユーザーキーは、合言葉と同じディレクトリ（0700）の別のファイル（0600）に置き、起動時に1回だけ読む。`-pushover` を指定しなければ、知らせずに画面のログにだけ番号を出す（試すとき用）
- 送るのに失敗したら、その要求は断る（番号を知る道がないので）
- Pushover の API に送るのは門番（`_monban`）。外への通信が1本増える

### 2-5. 数と時間

- 待ちの上限：2分。過ぎたら断る
- 同時に待てる要求：4つまで。超えたら断る（通知を溢れさせない）
- 接続の締め切り：いまは門番も `run` も30秒。承認を待つ間は延ばす（2分＋`bws` の分）

## 3. 聞きたいこと

### 3-1. どの要求に承認を求めるか

- 案A：全部の要求に毎回求める（v1 は簡単なほうで）
- 案B：許可リストの項目ごとに `"approval": "always" | "window"` を付ける。`window` は、一度承認した同じ組み合わせ（名札・秘密・コマンドの絶対パス・引数のハッシュ）を、決めた時間（例：10分）だけ承認なしで通す。design.md の「低リスクは時間枠つきの事前承認」
  - 心配：引数のハッシュまで揃えると、`curl` などは毎回引数が違って効かない。揃えないと、承認した後に引数を変えて送り先を変えられる（`hosts` で絞っていれば、その中だけ）
- 案C：承認なし（`"approval": "none"`）も許す。`printenv` の試しのように、承認が要らない項目
- どれがよいか。案B なら、何を揃えるべきか

### 3-2. 承認の番号を分ける案（2-2）は筋がよいか

- 8桁の数字・3回の外れで全部断る、で足りるか
- 番号をスマホにだけ出すことで、ターミナルの承認の強さを盛って書いていないか。書くなら、どこまで言ってよいか
- `approve` の接続も uid の照合だけで受けてよいか（同じ uid のエージェントも `approve` を送れる。番号を知らなければ通らない）

### 3-3. 承認の画面に出す引数

- 値は承認の後に取るので、承認の画面では「今回の秘密の値と一致する部分を伏せる」ができない
- 案：承認の前に取ってしまうと、拒否や時間切れでも門番に値が届く。承認の後に取るほうがよいと思うが、画面では伏せられない。引数の全文はそのまま出すか、出さずに数とハッシュだけにするか

### 3-4. Pushover まわり（2-4）

- 資格情報の置き場（合言葉と同じディレクトリ）でよいか。Bitwarden の秘密にして起動時に `bws` で取る手もある
- 送るのに失敗したら断る、でよいか
- メッセージに秘密の名前とコマンドを載せてよいか（Pushover の側に残る）

### 3-5. 承認と取り出しの順番

- 承認の後に `bws` で取ると、人は承認してから約0.5秒待つ。先に取っておくと、拒否のときも値が門番に来る。後に取る、でよいか

## 決まり（相談でも守る）

- 合言葉や本物のパスワードは、このリポジトリにも会話にも出さない
- 「見せない」の効果を盛らない
