# Muse の回答：門番 v1 の7段目（ログのハッシュ連鎖）

作成日: 2026-11-11
相談のメモ：[muse-consult-log-chain.md](muse-consult-log-chain.md)
Muse の回答を、相談の「聞きたいこと」の順にまとめた。貼られた回答は 3-5 の最後の段落の途中で切れていた（結論は読み取れた）。

全体：5つとも案の方向は合っている。

## 3-1. 末尾の切り捨て：B（起動と停止の行）＋C（門番の外に先頭のハッシュの写し）

- **B は入れる**。費用が小さい割に効く。前回の停止の行がないまま起動したら、画面とログの両方に目立つ形で出す。落ちたのか消されたのかは区別できないが、痕跡が残ることに意味がある。途中の行を消す・直すのは連鎖が見つけるので、B が見るのは末尾の側だけ、と役割が分かれる
- **C も入れる**。B だけでは「停止の行まで含めて1回分まるごと消された」ときに何も残らない。Pushover の側に、門番の外の写しが残る
  - 照らす手順と組にする：`monban verify-log` が「最後の seq と先頭のハッシュ」を出す。読み物に「ときどきスマホの知らせの番号と照らす」と書く。毎回ではなく、思い出したときの照合で足りる
  - 載せるのはハッシュの頭で、漏れても困る情報ではない
- **D（別の場所）は v1 では見送り**。root の持ち物のファイルに書くには、門番の権限の形を崩す。将来やるなら、macOS の統合ログ（`logger` でシステムの側に先頭のハッシュを流す）が、権限を増やさずに「別の場所」になる候補
- A だけは勧めない（B が安すぎる）
- 全部を計算し直す書き換えは、B＋C でも原理的には見つけられない。C の写しと照らして初めて「過去のある時点の先頭と違う」とわかる、が限界。これは「防げないこと」に書く

## 3-2. HMAC：読みは合っている

- 鍵に意味が生まれるのは、「鍵を読める人」と「ログを書ける人」の集合がずれるときだけ。今の設計ではどちらも `_monban` と root で一致するので、足しても守りは増えない
- 門番を「ログを書くプロセス」と「鍵を持つプロセス」に分ける日が来たら、そのときに初めて意味を持つ。v1 は1プロセスなので、なしで正しい

## 3-3. ログを読める人：0640＋専用グループを勧める（決めるのは9段目でよい）

- 監査のログは、本人が読んで初めて意味を持つ。0600 で毎回 `sudo` だと、誰も読まないログになる。`run` も「理由は門番のログを見てください」と言っている
- 同じグループ（＝同じ uid のエージェント）も読める件：読めるのは値・引数の全文・承認の番号ではなく、秘密の名前・コマンド・時刻・引数のハッシュという記録の要約。エージェントは自分の要求の分はもともと知っていて、増えるのはほかのエージェントの分の要約だけ。「防げないこと」に書けば、正直な引き換えとして成り立つ
- 今のうちに：起動時の確かめを「持ち主が `_monban`（試すときは自分）で、モードが 0600 か 0640、0640 のときはグループが専用グループと一致する」まで許す形にしておく。9段目でどちらを選んでも直しが要らない

## 3-4. 「これで防げないこと」の書き方

- ほぼ正確。2点直す：
  - **門番そのものが乗っ取られた場合を1行分けて書く**。連鎖が示すのは「書かれた後に、計算し直さない形では変えられていない」まで。門番のプロセスが乗っ取られていた間の行は、連鎖が正しくても中身は信用できない
  - **末尾の切り捨て**：「連鎖だけではわからない。起動・停止の行と、Pushover に送った先頭のハッシュとの照合で、気づける場合がある」。照合しなければ気づけないので「場合がある」を残す
- ほか（計算し直し、試すときの同じ uid）は、言い過ぎも足りなさもない

## 3-5. 細部

- **書きかけの最後の行で起動しない、は厳しすぎない**。ただし直し方を正確に案内する
  - 鍵は「ファイルが改行で終わっているか」。1行＋改行を1回で書く今の形では、途中で止まっても壊れるのは最後の不完全な断片だけ。逆に、末尾の完全な行を消すと、必ず改行で終わるファイルが残る
  - 改行で終わっていない＝書きかけ（完全な記録は1つも失われていない）。最後の改行の後ろを取り除けば直る
  - 改行で終わっているのに連鎖が合わない＝本物の異常
  - 「最後の行が書きかけです。最後の改行の後ろの断片だけを取り除けば起動できます」と出し、`verify-log` で「最後の完全な行が何バイト目までか」を示す
  - 起動時に門番が黙って切り取る（自動で直す）のは勧めない。証拠に手を入れるのは人の手で、と線を引くほうが、設計全体の姿勢と揃う
- **`prev` の形のままでよい**。各行に「その行までの累積のハッシュ」を持たせる形と、守りの強さは同じ。「ファイルに書いたバイト列そのものをハッシュする」という決めと相性がよい（ここで回答が切れていた）

## Muse の回答から、こちらで変えたこと

- **C の写しは、承認の知らせではなく、起動と停止の知らせに載せる**。承認の知らせには `ttl`（120秒）を付けていて、スマホから消える。写しとして残すには消えないほうがよいので、`ttl` を付けない別の知らせにした。起動と停止の知らせには承認の番号が入らないので、消えなくてよい。1回分まるごと消されても、その回の起動の知らせが残る
