## 3-1. ソケットの置き場 → A（`/var/db/monban-run/`）

- `/var/run` は、消えるかどうか以前に、権限だけで `_monban` には作れない。消えず、自分で持てる `/var/db/monban-run/` が素直。パスの長さの上限にも余裕がある
- B は root の助けが要る分だけ重い。C は cgo が要り、設計と合わない

## 3-2. 画面のログと承認の番号 → 本番でも残す。条件はファイルの 0600

- Pushover が届かないときに承認の道がなくなるのは、守りの仕組みとしての「使えること」の欠け。番号が読めるのは `_monban` だけ、が 0600 で守られるなら、残すほうがよい
- launchd が作るファイルの持ち主は確かめきれていないので、入れるときに 0600 `_monban` で先に作る案のままでよい
- **初めて起動した後に、持ち主とモードを目で確かめる**を手順に入れる

## 3-3. ログの置き場 → `/var/log/monban/` でよい

- 慣例どおりの場所。回さないのも7段目で決めたとおり

## 3-4. Pushover を本番で必須に → 賛成

- 本番の形（euid が持ち主の uid と違う）で Pushover がないと、番号は `sudo` でしか読めない場所にしか出ず、承認が事実上できない。起動のときに落とす（fail closed）のが正しい
- 試しの形は今のまま、の線引きも妥当

## 3-5. 止めた印 → ログに1行書く。印の中身は信じない、にも賛成

- 「止めたまま、何回起動しようとしたか」は、後から見返す価値がある。1行は安い
- 連鎖の決まりどおりに正しく足してから起動を断る形なら、確かめとも矛盾しない
- 中身（時刻・uid）は人が読むための表示で、門番は「あるかないか」だけを見る

## 3-6. 入れ方 → スクリプト1本。ただし「止まる」作りに

- 1行ずつの形は確かめやすいが、手順書と実物がずれていく。リポジトリに残るスクリプトは、それ自体が「何をしたか」の記録になる
- 条件は3つ：
  - 各ステップを画面に出しながら進む
  - 既にあるユーザー・置き場が想定と違えば、上書きせずに止まる
  - 合言葉には触らない（2-5 のとおり）
- uid は入れるときに空きを探す（400番台）でよい。**決まった番号はインストールの記録として残し、消すときと入れ直すときに同じ番号を使う**。名前と番号の両方の重なりを見る

## 3-7. 「これで防げないこと」 → 言い過ぎはない。半行ずつ2つ足す

- 「ソケットに繋げても、要求は許可リストと承認の対象のまま」を足す。今の文だと、繋げること自体が突破のように読める
- 「`_monbanusers` に人を足すと、その人もソケットとログに届く」を足す。将来の自分への注意として
- `sudo` の行と、許可リストが面倒になる行は、そのままで正確
