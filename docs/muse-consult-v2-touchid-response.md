# Muse の回答：v2 の「Touch ID の承認」

作成日: 2026-11-13
相談：[muse-consult-v2-touchid.md](muse-consult-v2-touchid.md)
読んだもの：相談文書、[design.md](design.md) の「門番の v1」と「正直に書くこと」、[v1-plan.md](v1-plan.md) の6段目、`cmd/monban/approval.go`、[muse-consult-gatekeeper-response.md](muse-consult-gatekeeper-response.md) の4
一次情報（2026-11-13 閲覧）：Apple TN3137「On Mac keychain APIs and implementations」、Apple「Protecting keys with the Secure Enclave」

## 結論

- **案 B を推す**。相談の見立てどおり。ただし強さの核は2層に分けて考えること：
  1. **指なしでは署名が作れないこと**は、鍵の結び付きが弱くても Secure Enclave が守る。鍵のアクセス制御が正しく付いていれば、誰のプロセスから署名を頼んでも、生体認証が通らなければ Enclave は署名しない。門番の1回限りの問い（nonce）への署名なので、使い回しもできない
  2. **画面に出た中身への承認であること**は、鍵がヘルパーだけに結び付いているときにだけ成り立つ。別のプログラムが鍵を使えるなら、そのプログラムが自分の文言で画面を出して指を当てさせ、門番の問いへの署名を取る道が残る。つまり実験3（ほかのプログラムから鍵を使えるか）は、案 B が「成り立つか」ではなく「どの格の強さになるか」を決める
- **鍵の所有者限定は、データ保護キーチェーンが前提**。TN3137 によると、生体認証での保護と Secure Enclave での鍵の保護は、どちらもデータ保護キーチェーンを必要とする機能で、そちらのアクセス制御は「キーチェーンアクセスグループ」で決まる。アクセスグループはコード署名の entitlement から作られ、その entitlement は provisioning profile の認可が要り、プログラムには profile を埋め込むアプリ風の包みが要る。だから「ad-hoc 署名でも足りるか」は楽観できない。実験で最初に潰すのはここ（4-4 の実験 0）
- 実験は 3-3 の4つでは足りない。先に署名と包みの実験（実験 0）が要り、後ろに画面の実物確認と鍵の失効・再登録の実験（実験 5・6）を足す

## 4-1. 案 A・B・C のどれか

### 案 B（推す）

残せる形の要点：

- **問い（challenge）の作り**：門番が承認のたびに作り、署名の対象に次を全部入れる。領域名の文字列（例 `monban-approval-v2`）、128ビット以上のランダムな nonce、リクエストの ID、エージェントの名札、秘密の名前、コマンド全文のハッシュ、有効期限。領域名を入れるのは、この鍵の署名がほかの用途の署名と取り違えられないため（署名の使い回し防止）。門番は「自分が出した・まだ使っていない・期限内」の問いへの署名だけを受ける
- **署名の形式を先に決める**：Secure Enclave の鍵は NIST P-256 のみ（Apple の文書どおり）で、署名・検証に使える。門番（Go 標準ライブラリ）で確かめるには、ヘルパーが返す署名の形式（X9.62 の DER なら `crypto/ecdsa` の `VerifyASN1` でそのまま確かめられる。生の R‖S なら変換が要る）と、公開鍵の書き出し形式（X9.63 の生形式か、SubjectPublicKeyInfo か）を仕様として固定する。これは実験4で確かめる中身でもある
- **ヘルパー側の受け口を絞る**：ヘルパーが署名してよいのは、門番から来た問いだけ。ヘルパーは受けた接続の相手の uid を確かめ、`_monban` でなければ断る（門番とヘルパーは uid が違うので、これは peer credential で確実に分かる。エージェントは `_monban` を名乗れない）。ここが崩れると、エージェントが門番の nonce を（偽ヘルパーとして受け取るなどして）手に入れ、ヘルパーに自分の文言で署名を頼む道が開く
- **登録（公開鍵の置き方）を門番の API にしない**：鍵の作成と公開鍵の登録は、入れる手順の中で、人のターミナル＋sudo で行う儀式に閉じる。門番に「公開鍵を差し替える口」があると、エージェントが自分の鍵（指なしでは使えないが、自分が指を当てる前提の偽物ではない。登録の瞬間を狙う）に差し替える攻撃面になる。公開鍵ファイルは root の持ち物で、門番は読むだけ
- **Touch ID の承認は同時に1つだけ**：`touchid` の項目では、承認待ちを1件に絞る（v1 の番号承認の `maxPending = 4` とは分ける）。割り込みの余地を小さくするため（4-2）
- **失敗は常に閉じる**：ヘルパーがいない・鍵が無い・指が通らない・期限切れ、は全部「断る」。`touchid` の項目を番号承認やパスワードに落とす道は、実行時にも登録のやり直し以外に作らない

弱さとして見落としやすいところ：

- **承認は「申告されたリクエスト」への承認**であって、「実際に動くプロセス」への承認ではない。コマンドが申告どおりかは、未実施の v1.5 候補（繋いできたのが本物の `monban run` かを確かめる）が入るまで保証しない。これは相談の 4-5 の案にもあるが、高リスクの秘密を `touchid` で解禁する前に、この穴を受け入れるのか、先に塞ぐのかを明示してほしい（私の見立て：`touchid` の解禁と、この穴の扱いの決定はセット）
- **鍵が使える画面の文言は、署名を頼むプロセスが決める**。ヘルパーが正規の経路で頼むときは門番から来た中身を出すが、システムの Touch ID 画面に載るのは理由の文字列と、頼んだアプリの名前まで。コマンド全文はヘルパーの自前の表示で見せることになるので、「Touch ID 画面に出す」は正確には「ヘルパーの表示＋Touch ID 画面の理由文」の2枚に分かれる。設計にそう書くほうが正直

### 案 A（単独では推さない）

- 実行ファイルの置き場と署名を確かめても、返ってくる「はい・いいえ」そのものはただのバイトで、確かめた相手と返事の結び付きは接続の瞬間にしかない（pid の取り違え、確認後に別プロセスが同じ接続を引き継ぐ形など）。案 B の署名は、この結び付きが暗号で残るところが違う
- ただし案 A の部品は無駄にならない。「本物の `monban run` か」の確認は、上の「申告どおりか」の穴を塞ぐ別件として残る。順番は v2 の後でよい
- なお、署名済みヘルパーへの入り込み（デバッガ接続、ライブラリ差し込み）は、Hardened Runtime＋ライブラリ検証つきで署名されたプロセスでは同じ uid からは素通りしない設計のはずだが、**未確認**。案 A を採るなら実験が要るし、案 B でもヘルパーの署名には Hardened Runtime を付けるのが前提（4-4 の実験 5）

### 案 C（案 B が崩れたときだけ）

- 同意。外のサービスに頼る部分が増え、承認の返し方そのものを他人に預ける形になるので、案 B の実験が全部落ちた場合の予備に留める

## 4-2. 同じ uid のエージェントにできること

- **偽の Touch ID 画面**：出せる。同じ uid のプロセスは、見た目を真似た窓を出すことを OS に止められない。ただし偽画面は指紋を読めないし、承認の署名も作れない。狙いは「偽画面で気をそらした直後に本物の画面を出し、反射で指を当てさせる」か「パスワードを打たせる偽画面でパスワードを釣る」の2つになる。対策：
  - 本物の承認では、Touch ID 画面の理由文に、ヘルパーの自前表示にも出す短い照合コード（nonce から作る数文字）を含める。人が「表示と画面のコードが同じか」を見られるようにする（見なければ意味がない、は 4-5 行き）
  - パスワードを打つ欄は、ヘルパーの自前表示には絶対に出さない。打つのはシステムの画面だけ、を運用の決まりとして書く
  - それでも残るので、「見た目の真似は防げない」は「防げないこと」に書く（4-5）
- **本物の待ちへの割り込み**：エージェントができるのは、自分の要求を正規の手続きで門番に出すことまで（許可リストと承認の対象）。同時に複数の Touch ID 承認が立つと、人がどれに指を当てるか取り違える余地ができるので、`touchid` は同時に1件・先の1件が終わるまで次は門番が作らない、で塞ぐ。エージェントがヘルパーに直接割り込む道は、ヘルパーが `_monban` 以外の接続を断れば開かない（4-1）。エージェントが偽ヘルパーを立てて門番の問いを受け取ることは、門番のソケットの置き場次第ではありうるが、問い自体は秘密ではない（ID・名前・ハッシュ）し、署名は鍵がなければ作れない。ただし受け取った nonce を持ってヘルパーに署名を頼みに行く組み合わせがあるので、ヘルパー側の uid 確認が要る、という連鎖になる
- **ヘルパーを止めて全部断る形**：できる。読みは相談どおり、妨害の棚でよい（秘密は出ない）。条件は2つ：①止められたことが門番のログに残ること（v1 の `monban stop` と同じ扱い）、②止まったときに承認が弱い形に落ちないこと（fail closed、4-1）。LaunchAgent の plist を `/Library/LaunchAgents/`（root の持ち物）に置く相談の判断は、この妨害を「置き換え」ではなく「停止」に留める意味でも正しい

## 4-3. 開発者の登録

一次情報で確かめた範囲：

- データ保護キーチェーンのアクセスグループは、entitlement を provisioning profile が認可して初めて使える（TN3137）。アプリ風の包みも要る。つまり「鍵をヘルパーだけ（または自前のアプリ群だけ）に結び付ける」には、**何らかの profile が要る**ところまでは確か
- 無料の Personal Team でも開発用の profile は発行できるが、monban-kit のヘルパーのように常駐して長く使う形で、profile の期限や署名の同一性（designated requirement）がどこまで安定するかは、**一次情報では確かめきれなかった（未確認）**。ad-hoc 署名は profile が無いので、アクセスグループの entitlement を主張できないはずで、データ保護キーチェーン側で鍵が作れないか、作れても結び付きが cdhash 頼み（作り直すたびに変わる）になる公算が大きい。これも未確認で、実験 0 で潰す

判断：

- **実験の段階では払わない**。まず手元の署名（Personal Team、だめなら ad-hoc）で実験 0〜3 を回し、「どの署名だと、どこまで結び付くか」の実測を取る。払うかどうかは、その結果への支払いにしたい
- **本番で高リスクの秘密を預ける段階で、安定した署名の同一性が有料でしか得られないなら、払う価値はある**。理由は、署名が不安定だと「作り直すたびに鍵へのアクセスが切れ、登録の儀式をやり直す」運用になり、面倒さが「ACL を広げる」「承認を弱くする」方向の圧力になるため。門番の本丸は承認の強さなので、その土台の同一性は金で買える部分なら買うのが筋。逆に、Personal Team で同一性が安定するなら払う理由はない
- 弱くなる形の明示：無償の範囲で済ませて結び付きが弱い場合、案 B の格は「指なしでは署名できない（第1層）」までで、「画面の中身への承認（第2層）」は落ちる。その状態で高リスクを預けるかどうかは、格を落としたことを design.md に書いてから決める。黙って混ぜない

## 4-4. 実験の順番

3-3 の4つの前に1つ、後ろに2つ足す。順番つきで：

- **実験 0（先頭に追加）：包みと署名**：LaunchAgent で動く最小の Swift 製ヘルパー（アプリ風の包み）が、データ保護キーチェーンに Secure Enclave の鍵を作れるか。署名の種類ごと（ad-hoc／Personal Team／もしあれば Developer ID）に、作れるか・アクセスグループがどう付くか・作り直しても同じ鍵に届くかを記録する。ここが全部の前提で、落ちたら案 B の形自体を見直す
- 実験 1：Touch ID の画面を出せるか（3-3 の1）。このとき、選んだアクセス制御のフラグで**実際に出る画面にパスコードへの逃げ道が出ないか**と、**続けて2回署名を頼んだときに2回とも指が要るか**（認証の使い回しが効いていないか）も一緒に記録する。「代わりの道はない」の設計は、ヘルパーの作りではなく鍵のアクセス制御で担保されるべきものなので、ここで実物を見る
- 実験 2：`biometryCurrentSet` の鍵を作れるか（3-3 の2）。署名の種類ごとに分けて記録する（実験 0 と結果を分けない）
- 実験 3：同じ uid の別のプログラムからその鍵で署名を頼めるか（3-3 の3）。結果は「頼めなかった」だけでなく、返ったエラーと、途中で**キーチェーンの許可を求めるシステム画面が出なかったか**まで記録する。許可画面が出て人が「常に許可」を押すと結び付きが崩れるので、出ること自体を設計の負けとして扱う
- 実験 4：Go の標準ライブラリで署名を確かめられるか（3-3 の4）。署名と公開鍵の形式（4-1）をここで固定し、テスト用の組（問い・署名・公開鍵）をリポジトリにダミーとして残す
- **実験 5（追加）：ヘルパーへの入り込み**：Hardened Runtime つきで署名したヘルパーに、同じ uid からデバッガ接続とライブラリ差し込み（`DYLD_INSERT_LIBRARIES`）を試し、できないことを確かめる。案 B でも、ヘルパーのプロセス内で署名の結果をすり替えられるなら署名の意味が落ちるので、これは案 B の実験でもある
- **実験 6（追加）：鍵の失効と登録のやり直し**：指紋を1つ追加すると `biometryCurrentSet` の鍵が死ぬことを確かめ、その状態で門番が fail closed になることと、登録の儀式（人のターミナル＋sudo）だけで復旧できることを通す。ついでに、蓋を閉じた状態（Touch ID が使えない）で断られることも見る

なお実験 3 は「頼めないことを確かめたい」が狙いだが、結果が「頼めた」でも案 B は捨てない。第1層（指なしでは署名できない）は残るので、その場合は格を落とした形（4-3）として設計を書き直してから進めるかを決める。

## 4-5. 「これで防げないこと」に書くこと

相談の案3点は妥当。そのまま入れてよい。足すもの：

- 見た目を真似た偽の承認画面は防げない。システムの Touch ID 画面そのものは偽れないが、その前後に自前の表示を割り込ませることは同じ uid のプロセスにできる。照合コードで「人が見れば分かる」までは作るが、見なければ効かない
- Touch ID は「登録されている指のどれか」であって「特定の人の指」ではない。家族の指が登録されていれば、その指でも承認になる。承認者の範囲は、この Mac に登録された生体認証の範囲と一致する
- 承認の疲れは防げない。短い間に何度も画面が出る使い方が続くと、人は中身を読まずに指を当てるようになる。同時1件と、項目を `touchid` に絞ることが、せめてもの歯止め
- 鍵の失効は止められない。指紋の追加・削除、Secure Enclave まわりの初期化で鍵が死ぬと、`touchid` の秘密は全部止まる。復旧は登録の儀式だけで、承認の格を落として通す道はない（可用性を承認の弱さで買わない）
- ヘルパーを止める・殺すことは防げない（妨害）。秘密は出ないが、`touchid` の承認は全部止まる。止まった事実はログに残る

言いすぎになるので入れないほうがよいもの：

- 「Touch ID で承認された要求は、申告どおりのものである」とは書けない（4-1 のとおり、実際に動くプロセスの保証は別件）。design.md 側の表現も「強い承認」は「渡すかどうかの判断が強い」の意味に限る、と寄せておくほうが正直

## 未確認（この回答で確かめきれなかったこと）

- 無料の Personal Team の provisioning profile で、常駐ヘルパーの署名の同一性が長期に安定するか（実験 0・2 で実測する）
- ad-hoc 署名でデータ保護キーチェーンの Secure Enclave 鍵が作れるか、作れた場合の結び付きの実体（実験 0・3 で実測する）
- Hardened Runtime つきヘルパーへの同じ uid からのデバッガ接続・ライブラリ差し込みが、実際にどこまで塞がれるか（実験 5 で実測する）
- 選んだアクセス制御フラグで、Touch ID 画面にパスコードの逃げ道が出ないか、Apple Watch の解除が指の代わりにならないか（実験 1 で実測する）
- Secure Enclave の署名の正確なバイト形式は、Apple の文書では「NIST P-256 の署名」までで、DER か生形式かは明記がなかった（実験 4 で実測して固定する）
