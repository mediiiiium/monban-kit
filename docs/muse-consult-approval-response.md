全体：流れ（待ち → 知らせる → 番号で承認 → 承認の後で初めて取る）は筋がよい。メモはこのままでよい。

## 3-1. どの要求に承認を求めるか

- **v1 は案A（全部・毎回）**。時間枠（案B）は「いつ・何を承認したか」の状態を持ち込み、いちばん間違えやすい。実際の要求の頻度と中身は、A で使ってから見える
- ただし許可リストの項目に `"approval"` の欄だけは今入れる。v1 で受け付けるのは `"always"` と `"none"` だけ。`"window"` が書かれていたら起動時に止める（黙って always にすると、本人の意図と違う動きになる）
- **案C（`"none"`）は許してよい**。既定にはせず、項目に明示したときだけ。「承認なし」は本人が選んだ項目だけに効く、と正直に書ける
- 将来 B を入れるとき：揃えるのは「名札・秘密・コマンドの絶対パス・送り先のホストの組」まで。引数のハッシュは揃えない（`curl` では毎回ずれて枠が効かない）。枠の中で守っているのは「値の送り先」で、そこが境。窓は短く（10分は妥当）、拒否されたら同じ組の窓を消す

## 3-2. 承認の番号を分ける案

- 筋はよい。強さの書き方も盛っていない（「試している間は上がらない」まで書いてあるのが正しい）
- **8桁＋外れ3回で全部断る、で足りる**。試すことが音を立てるから。3回外して全部断たれた後、もう3回試すには新しい要求を出すしかなく、そのたびにスマホに知らせが行く。桁を増やすより、この「試す＝知らせが行く」の形が効いている
- 本番の形で言ってよいこと：「承認には、Pushover（スマホ）と門番の画面のログにしか出ない1回限りの番号が要る。本番の形では、ユーザーの uid からはそのどちらも読めない」
- 並べて書くこと：番号は Pushover のサーバーとスマホの通知を通る。人が番号を打ったコマンドは、シェルの履歴と、動いている一瞬の引数（`ps`）に残る。ただ番号は1回限りなので、後から見ても使えない
- 細部：番号は `crypto/rand` で作る。先頭のゼロを含む8桁の決まった長さの文字列として比べ、Pushover にもゼロ埋めで出す（`00123456` を `123456` と打って外れる、を防ぐ）
- `approve` の接続を uid の照合だけで受けるのは問題ない。番号そのものが資格情報で、uid の照合は外側の柵。外れたときの返事は理由を分けず一律にし、外れは繋いできた uid・pid と一緒にログに残す

## 3-3. 承認の画面に出す引数

- **全文を出す**。数とハッシュだけでは、何をするコマンドか人が判断できず、承認の意味がなくなる
- 値と一致する部分を伏せられない件は、ほぼ無害。引数に今回の値が入っているなら、エージェントがもう値を知っている場合だけ（値はまだ渡っていないので、知らない値は書けない）
- 気をつけるべきは別の秘密（ヘッダのトークンなど）だが、出す先は本人のターミナルで、本人が目で確かめる場所。線引きは今までどおり、画面には全文、ファイルのログには数とハッシュだけ

## 3-4. Pushover まわり

- **資格情報の置き場**：今の案（合言葉と同じ 0700 のディレクトリの 0600 のファイル）でよい。Bitwarden から起動時に取ると起動の依存が増え、「取れなかったら知らせられず、承認できる要求が1つもない」という止まり方をする。置き場の守り（読めるのは `_monban` と root だけ）はどちらも同じ
- **送れなかったら断る**：正しい。番号を知る道がない要求を通す理由はない。`-pushover` を指定しないときは画面のログだけ、という試す形も問題ない
- **載せるもの**：秘密の名前とコマンドは載せてよい（値ではなく、ログにも残る種類の情報）。「名前とコマンドは Pushover のサーバーとスマホに残る」と文書に1行入れる。値は決して載せない
- 安い工夫：Pushover には有効期限（`ttl`）を付けて送れる。待ちの上限（2分）に合わせると、スマホに残る番号の写しが早く消える。優先度は通常で足りる（緊急の優先度の受領確認は承認の代わりにならない）

## 3-5. 承認と取り出しの順番

- **承認の後に取る、で正しい**。0.5秒の待ちは小さく、拒否・時間切れ・見捨てられた要求では、値が Bitwarden の外に出ない。門番のメモリに値がある時間も短くなる

## ほかの細部

- 締め切りを延ばすのは「待ちに入った接続」だけ。`approve` などほかの接続は今の30秒のまま
- 承認の画面に、要求が来てからの経過（残り時間）も出す
