# Muse への相談：門番 v1 の7段目（ログのハッシュ連鎖）

作成日: 2026-11-11
読んでほしいもの：[v1-plan.md](v1-plan.md)（3段目の「最小のログ」、6段目まで、「これで防げないこと」）、`cmd/monban/audit.go`
前回までの相談と回答：[muse-consult-v1-plan-response.md](muse-consult-v1-plan-response.md)（ログを2つに分ける）、[muse-consult-approval-response.md](muse-consult-approval-response.md)

## 1. ここまでの進み

- 6段目（承認）を作り、本物の合言葉（試用のもの）と本物の Pushover で、人のターミナルで確かめた
- 今のログ（`audit.log`）は、1行1つの JSON を末尾に足すだけ。開くときは `O_APPEND|O_NOFOLLOW`、門番の持ち物で 0600 の普通のファイルでなければ起動しない。書けなければ値を渡さない
- 書く行：要求1回につき1行（断った・渡した・承認の画面に出した・承認された など）、`approve`・`deny`・`show` の接続1回につき1行、起動時に `userOwned` の項目があればその行。値・引数の全文・承認の番号は書かない
- 今は、門番と同じ uid なら書き換えられる。本番（9段目）では `_monban` の持ち物にするので、ユーザーの uid からは書けなくなる

## 2. 案（こう作るつもり）

### 2-1. 形

- 各行に `seq`（1から始まる通し番号）と `prev`（1つ前の行のバイト列の SHA-256、16進）を足す。最初の行の `prev` は `0` を64個並べた値
- ハッシュは、ファイルに書いた1行のバイト列そのもの（改行は除く）から取る。JSON を整え直してからは取らない（並び順や書き方の揺れで合わなくならないように）
- 門番は最後の行のハッシュと `seq` をメモリに持ち、今の mutex の中で次の行を作って書く

### 2-2. 起動時

- 今あるログを頭から読み、連鎖を確かめてから、最後の行の続きから書く
- 途中で連鎖が切れている・`seq` が飛んでいる・最後の行が改行で終わっていない（書きかけ）・JSON として読めない、のどれかなら起動しない。どの行で切れたかを画面に出し、人に判断を任せる（黙って直したり、新しいファイルに切り替えたりしない）
- 連鎖の欄のない行（6段目までの試しのログ）があるファイルでも起動しない。今あるのは試しのログだけなので、どけてもらう

### 2-3. 確かめるコマンド

- `monban verify-log <ファイル>` を足す。頭から確かめ、「何行・最後の seq・最後のハッシュ」か、「何行目で切れた」かを出す。門番を動かしていなくても使える

### 2-4. やらないつもりのこと

- 鍵つき（HMAC）にはしない（→ 3-2）
- ログを分けたり回したりはしない（v1 は1つのファイルに足し続ける）

### 2-5. これで防げないこと（書くつもりの案）

- 鍵のない連鎖なので、ファイルを書き換えられる人は、書き換えた後に連鎖を全部計算し直せる。わかるのは、うっかりの壊れと、計算し直さない書き換え（途中の行を直した・消した・入れた）まで
- 末尾の何行かを消されると、連鎖だけではわからない（→ 3-1）
- 試すとき（門番を自分の uid で動かす）は、同じ uid のエージェントがログを書き換えて計算し直せる
- 本番の形では、ユーザーの uid からはそもそも書けない。連鎖が見つけるのは、root か `_monban` を取った誰かが、計算し直さずに書き換えた場合と、壊れ

## 3. 聞きたいこと

### 3-1. 末尾の切り捨て（と全部の計算し直し）を見つける手

案：
- A：何もしない。末尾の切り捨ては見つけられない、と書く
- B：起動と停止の行を書く。止めた行がないまま次に起動したら、画面とログに出す（落ちたのか、消されたのかは区別できない）
- C：連鎖の最新のハッシュの頭の8文字を、Pushover の知らせに載せる。スマホと Pushover のサーバーに、門番の外の写しが残る。ただ、人が照らす手順がないと意味がない
- D：別の場所（例：root の持ち物のファイル、または別のマシン）に最新のハッシュを書く。v1 には重い

どれがよいか。組み合わせるならどれか。

### 3-2. 鍵つき（HMAC）にする意味

- 鍵の置き場は、合言葉と同じ 0700 のディレクトリしかない。本番では、鍵を読める人（`_monban` と root）はログも書ける
- だから鍵をつけても、ファイルの権限に足して守れるものはほぼないと思う。この読みで合っているか

### 3-3. ログを読める人

- 本番ではログが `_monban` の持ち物で 0600 になり、本人（ユーザーの uid）は自分のログを読めない。`verify-log` も `sudo` が要る
- 案：ログを 0640 にして、ソケットと同じ専用グループに読ませる。ただ、同じ uid のエージェントもそのグループにいるので、ログを読める（値・引数の全文・番号は書いていないが、秘密の名前・コマンド・時刻・`args_sha256` は読める）
- 0600 のまま `sudo` で読むか、0640 で読ませるか。9段目で決めればよいか

### 3-4. 2-5 の書き方

- 言い過ぎも言い足りなさもないか

### 3-5. 細部

- 書きかけの最後の行（ディスクが一杯になったときなど）で起動しない、は厳しすぎないか。人がその行を消せば起動できるが、それは「末尾を消す」と同じ操作になる
- `prev` の代わりに、各行に「その行までのハッシュ」を書く形もある。どちらでもよいか

## 決まり（相談でも守る）

- 合言葉や本物のパスワードは、このリポジトリにも会話にも出さない
- 「見せない」の効果を盛らない
