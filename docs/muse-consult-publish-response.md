## 3-1. 公開してよいか → 公開してよい。注意書きは冒頭にも置く

- 守りの穴の一覧を出すことは、攻める側への手がかりにはなりにくい。載っている穴はどれも「root が取れている」「同じ uid で動いている」が前提で、その時点で相手はもう中に入っている。新しい攻撃の作り方を渡す内容ではない
- 防御の道具は、限界を書いて公開するのが普通の形。限界を隠すほうが、使う人が過信して危ない
- 本当のリスクは、読んだ人が v1 を高リスクの秘密に使ってしまうこと。README の注意書きは今の位置（これで防げないこと）に加えて、冒頭にも1行置く。「v1 は高リスクの秘密を扱わない。ターミナルの承認は事故防止であって、強い承認ではない」が伝わる形に
- 公開の順番：全文の確かめ（3-3）が済んでから。あとで公開し直すと確かめをやり直すことになる、という相談メモの見立てどおり、Zenn と一緒に済ませるのがよい

## 3-2. 公開から外すもの

- `muse-consult-*` と `muse-note-*` は残してよい。決めた理由の記録はこのキットの特徴で、記事でも触れている。ただし全文の確かめの対象には含める（相談の往復には、個人の環境寄りの値が混ざりうる）
- `mac-autofill-setup.md` は外す、で同意。ほかに外す候補は `muse-note-agent-framework.md`。門番そのものの話ではなく、本人の環境（エージェントの枠組み）のメモなので、利用者には要らない。残す理由も薄い
- 消し方：中身が「関係ないだけ」で機密でないなら、今のファイルから消すだけでよい。ただし今は非公開で履歴も小さい（37コミット）ので、全文の確かめで個人寄りの値（実名・ホームのパス・メール・IP）が1つでも出たら、その機会に履歴ごと消す（書き換えて force push）。公開した後では履歴の書き換えは高くつくので、迷ったら今のうちに履歴ごと、が安い

## 3-3. 公開の前に確かめること（grep に足す）

- grep だけでなく、docs の全文を人の目（reviewer）で読む。今の計画どおり
- 機械で拾う観点を足す：
  - 実名（漢字・ローマ字）と、ホームのパスの別形（`/Users/<名前>`、`~` 展開済みの値）
  - Tailscale の IP（100.x.x.x の形）と、Mac のホスト名
  - 合言葉らしい形の文字列（`0.` で始まる長い文字列など、トークンの形をしたもの全般）を、履歴の全コミットに対して
  - 承認の番号が、ログの引用として docs に残っていないか
- uid（501・401）と launchd のラベル（`io.github.mediiiiium.monban`）は出してよい。mediiiiium は note・GitHub で公開している名前で、uid はそれ自体では何も漏らさない
- `.gitignore` の漏れは、追跡しているファイルだけでなく、追跡していないファイル（`git status` の untracked）と、全ブランチ・タグ・stash も見る。公開は今の main だけとは限らない
- 画像ファイルがあれば、写っている中身も見る
- reviewer への観点の足し分は上記のとおり。「個人寄りの値」の定義を、本人の名前・住所的なパス・IP・メール・トークンの形、まで具体的に渡すと拾い漏れが減る

## 3-4. LICENSE と受け付けるもの → MIT。issue は開け、対応は約束しない

- LICENSE は MIT でよい。保証しない条項（AS IS）は MIT の中にもともと入っている。それでも README の注意書きは別に要る（ライセンスは法的な無保証、注意書きは使い方の線引きで、役割が違う）
- issue は開けておくのを勧める。理由は2つ。使う人の質問が集まる場所が要ることと、守りの穴を見つけた人が知らせる先が要ること。後者のために、GitHub の private vulnerability reporting（非公開の脆弱性報告）を有効にしておくと、公開 issue に穴の細部が書かれずに済む
- 受け付けの姿勢は README に1行：「個人のプロジェクトです。保守はベストエフォートで、issue・PR への対応とマージは約束しません」。PR は GitHub の仕様で完全には閉じられないので、閉じる代わりにこの1行で受ける

## 3-5. Zenn に載せるコードの範囲 → 要所でよい。環境の値は載せない

- 載せてよい：考え方が伝わる要所（相手の uid の確かめ、`exec` の前にソケットを閉じるところ、許可リストの見せ方など）。リポジトリの該当行へのリンクを付ける案でよい
- 署名の確かめの細部も、承認の番号の作り方も、載せて問題ない。防御はその存在と運用であって、細部を隠すことではない（一般的な実装でもある）
- 載せないもの：本人の環境そのままの値。実在のパス・uid・ラベルは、記事の中では一般的な形に置き換える。実物のログの行（本当のリクエスト ID や時刻）も載せず、例として作った形にする
