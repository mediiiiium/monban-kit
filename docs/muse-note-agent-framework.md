# Muse とのやり取りのメモ：エージェントの枠組みと、門番の広がり

作成日: 2026-11-11
きっかけ：「VMのAIエージェントが集まる場所」という考えから始まった検討。記事（note「Museをしばらく使ってみて」）とは別の、仕組みとしての検討経過。内容は本人が確認しながら進めたもの。

## 検討の流れ

1. **「各サービスのログインを持つエージェントが集まる場所」ができるのでは**、という本人の着想
2. 調べて分かった現状：企業向けには A2A（Agent2Agent）という共通規格が先行している（2026年3月に v1.0、150団体超）。コロプラの社内ハブの例では、どの場からどのエージェントを呼べるかを、持ち主同士の事前の合意で決め、AI には判断させない。サービスへの接続側は MCP が担当
3. ただし個人のエージェント（各社のアプリの中の存在）は庭から出てこない。API で呼べるのはモデル（頭脳）だけで、「ログイン＋記憶＋道具」を持ったエージェントそのものは外から呼べない。自分で組み立てたエージェント（Claude Code、Codex）は持ち主が本人なので、リレーで回せている
4. **本人の結論（構成案）**：
   - 実行役は1人：VM に常駐するエージェントが、ログイン・記憶・道具を持って作業する
   - 議論役は複数モデル：API で呼んで意見を戦わせ、結果を実行役が受ける
   - 「集まる場所」は要らない。要るのは共有の黒板（文書・リポジトリ）と、黒板が更新されたら関係するエージェントが自動で気づく通知の仕組み（差分つき。定期的に見に行く方式は予備）
   - 人間は各サービスの UI を行ったり来たりせず、1つの窓口だけ見る

## 枠組み（部品と原則）

部品：①常駐エージェント（住人） ②黒板（共有文書） ③更新の通知 ④議論役のモデル群（状態を持たない） ⑤門番（許可層）

原則：
- 状態を持つのは住人だけ。モデルは使い捨ての頭脳
- 共有は会話ではなく文書で。「黒板に書かれていないことは起きていない」
- 許可は事前の合意で決め、AI にその都度判断させない
- 全部ログに残る（誰が何を見て、誰の意見で、何をしたか）
- 体験としてはシームレスであること。仕組みは裏側に引っ込み、表に出るのは承認が要る瞬間だけ（あの摩擦は意図的に残す）

## 門番（monban）との関係 — 本人が腑に落ちた点

- 「黒板のどこまで見せるか」は、実行の制御と同じかそれ以上に大事。実行は承認やキルスイッチで止められるが、**見せた情報は取り消せない**。議論役は外部のモデルで、渡すたびに社外送信になる
- これは社内の文書管理の機密ラベルと同じ構造：文書にラベルを付け、相手ごとに渡せる上限を決め、要約は「ラベルを下げる加工」
- つまり門番のパターン（許可リスト・承認・ログ）は、合言葉だけでなく情報の流れ全体に広げて使える。monban-kit は、その部品を最初に作った場所という位置づけ
- 門は3つ：情報の門（見せる範囲）、実行の門（承認）、通知の門（どの更新を誰に知らせるか）

## 読み手への見せ方（本人の指摘）

- 部品の名前（黒板・住人・門番）から入ると、初めての人には分かりにくい。比喩は実物を見た後でないと効かない
- 順番は「実景（AI 同士の相談を人がファイルで運んでいる）→ 部品に名前を付ける → 原則は最後」

## 次にやること（案）

- 試作の最小形：monban の相談リレーで、今は本人が「読んで」と運んでいる部分だけを自動化する（相談文書が更新されたら通知が来て、Muse が読みに行く、という1本の線）。黒板・通知・住人の3つが最小で回る
