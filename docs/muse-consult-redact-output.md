# Muse への相談：v1.5 の「出力から秘密の値を伏せる」

作成日: 2026-11-13
読んでほしいもの：[design.md](design.md) の「v1.5 の候補」、[v1-plan.md](v1-plan.md) の5段目と「これで防げないこと（v1）」、`cmd/monban/run.go`、`tools/pushover-notify`
前回の相談と回答：[muse-consult-publish.md](muse-consult-publish.md)、[muse-consult-publish-response.md](muse-consult-publish-response.md)

## 1. なぜ今これか

- v1 は10段すべて作り、本物の秘密を1本（Pushover のトークン、低リスク）通した。高リスクの秘密はまだ預けていない
- 次は v1.5 の「出力を伏せる」から始める（2026-11-13 に決めた）。理由：
  - 高リスクの秘密を預けたい場面がまだ来ていないので、強い承認（v2 の Touch ID）は後でよい。実際に困った順に作る
  - 今の1本にも効く。注入先のコマンドがうっかり値を出しても、画面やエージェントの会話に残らない
  - v1.5 のもう1つ（本物の `monban run` かを実行ファイルで確かめる）は cgo が要り、「標準ライブラリだけ」の方針とぶつかるので後に回す

## 2. 先に気づいたこと：伏せられるのは門番ではなく `run`

- 前の回答（[muse-consult-gatekeeper-response.md](muse-consult-gatekeeper-response.md)）は「門番は値を知っているので、出力から完全一致を探して伏せる処理は安く足せる」だった
- ただ、今の作りでは門番はコマンドの出力を見ない。`run` が値を受け取り、`syscall.Exec` で注入先のコマンドに置き換わる。出力はコマンドから端末（エージェント）に直接出る
- だから伏せるには、`run` を `exec` ではなく**親として残し**、コマンドを子として動かして、子の stdout と stderr をパイプで受けて書き直してから流す形に変える要がある
- 門番がコマンドを動かす形（代理実行、段 C）にすれば門番の側で伏せられるが、v1 に入れないと決めた範囲。今回は `run` の側でやるつもり

## 3. こう作るつもり（案）

- `monban run` は、値を受け取ってソケットを閉じたら、`exec` の代わりに子としてコマンドを起動する（パスは今までどおり門番に送った絶対パス）
- stdin はそのまま子に渡す。stdout と stderr はそれぞれパイプで受け、分けたまま流す
- 伏せ方：
  - 値と完全に一致するバイト列を `[monban: 伏せた]` に置き換える
  - 書き込みの境目で値が2つに割れても見逃さないよう、末尾のうち「値の先頭と一致している部分」だけを手元に残し、続きが来てから決める。一致しないと分かった分はすぐ流す（待たせるのは、値の先頭と一致している間だけ）
  - 子が終わったら、残りを流す
- 子の終わり方をそのまま返す：終了コードはそのまま。合図で死んだら 128＋番号
- `run` が受けた SIGINT・SIGTERM・SIGHUP は子に渡す
- 子が孫を残してパイプを握ったままでも、子が終わってから一定の時間（`bws` と同じ2秒）で待つのをやめる
- 伏せたときは stderr に1行（`monban run: 出力から秘密の値を N か所伏せた`）。値は出さない
- 伏せる処理は毎回かける。切る口は作らない（切りたい場面が出たら考える）

## 4. 聞きたいこと

### 4-1. `exec` をやめて親として残ることの重さ

- v1 で守ってきた「受け取ったらすぐ `exec`。`run` のメモリの値はそこで消える」が崩れる。`run` は子が終わるまで値をメモリに持ち続ける
- こちらの読み：同じ uid からは、子の環境変数が `ps eww` でもともと見える。`run` のメモリに値が残っても、見える場所が1つ増えるだけで、守りの段は変わらない。これで釣り合っているか
- `exec` の形を残し、伏せる形と選べるようにするべきか（たとえば許可リストの項目ごと）。こちらは「選べると、伏せない形が選ばれ続ける」ので毎回かけたい

### 4-2. 端末を握るコマンド

- パイプにすると、子からは stdout・stderr が端末に見えなくなる（色が消える、行ごとにまとめて出す、進み具合の表示が変わる、対話のコマンドが動かない、など）
- 門番を通すのは、Pushover に送る・API を1回叩く、のような対話のないコマンドを考えている。端末を握るコマンドは「伏せられないので許可リストに入れない」と書けば足りるか
- 子が `/dev/tty` を開いて直接書くと、パイプを通らないので伏せられない。これは「防げないこと」に書くだけでよいか

### 4-3. 一致の範囲

- 完全一致だけにするつもり。値を変えた形（base64、URL エンコード、JSON のエスケープ、前後の空白を落としたもの、一部だけ）は伏せない
- 足すとしたら、どの形までが釣り合うか。こちらは「完全一致だけ」にして、伏せた形の一覧を広げるほど「伏せてくれる」と思い込ませる、と考えている
- 短い値（数文字）は、関係のない出力まで伏せてしまう。値が短いとき（たとえば8バイト未満）は伏せずに起動を断るか、伏せずに通して1行知らせるか

### 4-4. 伏せたことを残す場所

- `run` はユーザーの uid で動くので、門番のログ（`_monban` の持ち物）には書けない。伏せた事実は stderr の1行だけになる
- 門番のログにも残すべきか。残すなら、子が終わってから `run` が門番にもう1回繋いで「ID … で N か所伏せた」と知らせる形になる。ただ、これは `run` の申告なので、エージェントが黙らせることもできる。釣り合うか

### 4-5. 「これで防げないこと」に書くこと（案）

- 伏せるのは、子とその孫が stdout・stderr に書いた、値と完全に一致するバイト列だけ
- ファイルへの書き込み、ネットワークへの送信、`/dev/tty` への直接の書き込みは伏せない
- 値を変えた形（base64 など）、値の一部は伏せない
- `run` は同じ uid で動くので、エージェントは `run` を通さずに値を扱う道（子の `ps eww` など）を今までどおり持っている。伏せるのは事故で出た値を会話に残さないためで、盗もうとする相手は止めない
- 足りない、言いすぎ、のところがあれば教えてほしい

## 決まり（相談でも守る）

- 合言葉や本物のパスワードは、このリポジトリにも会話にも出さない。試すときの秘密はダミーの `MONBAN_TEST` だけ
- 「見せない」の効果を盛らない
