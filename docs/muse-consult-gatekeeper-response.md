# Muse の回答：門番の実装をどう始めるか

作成日: 2026-11-10
相談のメモ：[muse-consult-gatekeeper.md](muse-consult-gatekeeper.md)
Muse の回答を、相談の「聞きたいこと」の順にまとめた。末尾の「未確認」は、Muse が書いたがまだ確かめていない点。

## 1. どの案から始めるか → B（薄い門番を自作）

- 試用でわかった核心は、ポリシー（許可リストや承認の作法）ではなく**合言葉の置き場所**
- A（mcp-warden 拡張）：同じユーザーで動く前提なので、置き場所の問題を解かない。足すのは金庫の部分だけで、それは一番軽い。作者が受け入れるかも決まっていない。設計（許可リストの書き方、時間枠つき承認、ハッシュ連鎖のログ）だけ借りる
- C（R055LE 移植）：別ユーザー＋別デバイス承認の形は正しい。ただ systemd と Linux キーリングを launchd とキーチェーンに移すのは、新しく書くのとほぼ同じ手間。設計だけ借りる
- B：重い部分は借り物で済む（金庫は `bws`、承認の段取りは A と C）。書くのは「保管・許可リスト・承認・ログ・注入」の薄い層だけ
- 別の案：**Linux VM の中に門番を置く**（C がそのまま動く）。隔離は一番強いが、常駐 VM は個人用には重い。別ユーザーで足りない高価値の秘密が出たときの逃げ道として残す

## 2. 最初の版（v1）で削るもの

- 残す：別ユーザーのデーモン、読むだけ、許可リスト、ログ、キルスイッチ、`monban run` 形の注入
- 削る：
  - MCP（CLI のラッパーなら Claude Code でも Codex でも同じ形で使える。MCP はエージェントごとに設定が違う）
  - 代理実行（段 C）
  - Touch ID と GUI の承認。v1 の承認は、本人が自分のターミナルで打つ承認コマンド。位置づけは事故防止（6を参照）
  - **高リスクの秘密は v1 では扱わない**。強い承認（スマホか Touch ID）が付くまで、門番に預けるのは低・中リスクだけ
  - Windows 対応、ログイン情報の JSON 規約

## 3. 言語 → Go。`bws` は子プロセスで呼ぶ

- Go：単一バイナリで配れる。ランタイムが要らない。Unix ソケットもデーモン化も標準ライブラリで足りる。起動が速い
- `bws` は子プロセス：SDK の Go 向けバインディングは薄く、実質 FFI になる。子プロセスなら、試用でやった「リリースを落としてチェックサムを照合」がそのまま使える。門番の起動時に `bws` の署名（TeamIdentifier `LTZ2PFU5D6`）を確かめれば、すり替え対策になる
- 合言葉は**環境変数**で `bws` に渡す。引数は `ps` で見えるので使わない
- 1回の呼び出しにかかる時間を v1 で測る。遅ければ、`bws` を常駐させる形をそのとき考える

## 4. 別ユーザーの門番から承認を出す方法

- launchd のデーモン（別ユーザー、ログインのセッションの外）からは、GUI も Touch ID も出せない
- 部品を2つに分ける：
  - **門番デーモン**（`_monban`。合言葉を持つ。画面は持たない）
  - **セッション側のヘルパー**（LaunchAgent。ログイン中のユーザーで動く。合言葉も秘密の値も持たない。承認の表示と結果の返送だけ）
- ヘルパーは LocalAuthentication で Touch ID を出せる。ヘルパーを通るのは、リクエストの ID と「どのエージェントが・どの秘密を・何のために」の事実だけ
- design.md の未確認「別ユーザーで動く門番から Touch ID の確認を出せるか」への答え：門番自身は出せない。セッション側に相方を置けば出せる
- 順番：v1 はヘルパーを作らず、**スマホへの承認依頼（Pushover）**を先にする。別デバイス＋スマホ側の生体認証で、ターミナルの承認コマンドより一段強い。Touch ID のヘルパーは v2

## 5. 渡し方 → 注入（段 B）が先

- 代理実行（段 C）は、相手のサービスごとにアダプタが要る。汎用のものはないので、先に作ると全体が遅れる。高価値の少数にだけ後から足す
- 注入の既定は**コマンド単位**にする。秘密は、それを使うコマンドのプロセスにだけ渡り、エージェントに見えるのは標準出力だけになる
- エージェント全体への注入（`bws run -- claude` の形）は、弱い形として残してもよいが、既定にはしない

## 6. 見落としている穴

- **「どのエージェントか」は認証ではない**。Unix ソケットの相手の資格情報でわかるのは uid まで。Claude Code も Codex も同じ uid。許可リストのエージェント欄は名札で、なりすましは防げない。守りの実体は uid の分離と承認
- **承認の偽造**。ユーザーのセッションの中で終わる承認（ターミナルの承認コマンド、ダイアログのクリック）は、同じユーザーのエージェントが原理的には真似できる（`osascript` など）。高リスクの承認は、生体認証か別デバイスに限る
- **失効の遅れ**。合言葉を失効させても最大1時間は読める。キルスイッチは「即時遮断」ではなく「門番の停止＋失効の手続き。最大1時間は残る」と書く
- **出力からの漏れ**。注入先のコマンドの出力やエラーに秘密が混ざると、エージェントの会話に残る。門番は値を知っているので、出力から完全一致を探して伏せる処理は安く足せる（v1.5 の候補）
- **ログの置き場所**。ログを `_monban` の持ち物にすれば、ユーザー側のエージェントから書き換えられない。別ユーザー方式の隠れた利点
- **マシンアカウントは Can read のまま固定**。門番が乗っ取られても、秘密の書き換えや削除はできない。これを変えない決まりにする

## まとめ

「B を最小で作り、A の設計を借りる」で進めてよい。C からは「別デバイス承認」の段取りを借りる。v1 の線引きは「高リスクの秘密は扱わない」。

## 未確認（Muse の回答のうち、まだ確かめていないこと）

- 別ユーザーのプロセスの環境変数は、ほかのユーザーからは `ps eww` で読めない（macOS で試していない）
- launchd のデーモンからは Touch ID を出せず、LaunchAgent のヘルパーからなら LocalAuthentication で出せる
- `bws` の SDK の Go 向けバインディングは薄い
- `bws` の1回の呼び出しにかかる時間
